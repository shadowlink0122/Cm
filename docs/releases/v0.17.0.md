# Cm v0.17.0 リリースノート（開発中）

**前バージョン:** v0.16.2

## 🎯 テーマ: JS/TSエコシステム連携（npmパッケージ・React/Nodeへの道）

### 標準ライブラリ: 平衡二分探索木マップ（std::collections::TreeMap）

- **`TreeMap<K, V>` を追加**: 自己平衡二分探索木（AVL木）による順序付き連想コンテナ。探索・挿入が **O(log n)** で、線形探索の連想配列より要素数増加に強い。木はインデックス参照のノードアリーナ（パラレルな動的配列）で表現し、ノード参照はポインタでなくindexで持つため全バックエンド（jit/native/wasm/js/ts）で同じ動作をする
- キー型 K は順序比較（`<`・`==`）が必要（int/string等は組み込み、構造体は `with Ord, Eq`）。値型 V は任意。API: `put`/`get`/`contains`/`size`。挿入ごとにAVL回転で平衡化し、ソート済みキーでも高さが対数に収まる（100件ソート挿入で高さ約7）
- ノードアリーナは動的配列（スライス）で、`put` のたびに容量が足りなければGoのスライスと同様に容量が2倍ずつ自動拡張される。要素数に固定上限は無く、固定長配列を使わないので native の AOT 最適化コンパイル時間も要素数に依存しない（treemap_testの -O2 コンパイルは約0.7s）
- あわせて動的配列（スライス）まわりのコンパイラ・ランタイムバグを修正:
  - **implメソッド内の `self.slice_field.push(x)` 等が黙って捨てられていた問題を修正**: メンバスライスの場所を解決する `get_member_place` が、implメソッドの `self`（`*Struct` ポインタ）を土台にできず false を返していたため、`self.items.push(...)` のような文がMIRから丸ごと欠落していた。ポインタ土台のときは Deref を挟んで pointee 構造体からフィールドを辿るよう修正。構造体フィールドの動的配列が全バックエンドで正しく in-place 更新される
  - **ジェネリックなスライスフィールドの要素サイズが誤っていた問題を修正**: 型置換 `substitute_type_in_type` に配列（`Array`）ケースが無く、`K[]` の要素型が未解決（`K`）のまま残っていた。要素サイズ計算がこれをblob扱いして `int` を12バイトとみなし、push（4バイト書き込み）とindexアクセスの stride が食い違っていた（バッファに余裕のないwasmで木構造が壊れた）。`Array` の element_type を再帰置換するよう修正
  - **WASMのバンプアロケータがプール枯渇時に生きている割り当てを上書きしていた問題を修正**: 64KB固定プールを使い切ると先頭へ巻き戻して既存データを踏み潰していたため、スライスを多用する処理が一定サイズで構造体フィールドやスライスヘッダを壊していた。巻き戻しをやめ、枯渇後は `memory.grow` で線形メモリを拡張して新領域から配るようにした。あわせてWASMの `cm_slice_grow` が旧ブロックサイズ超えでコピーしていた点と、`cm_free` がWASMランタイムに未定義だった点を修正
  - **ジェネリックのモノモーフ化を不動点まで反復するよう修正**: メソッドチェーン `A()->B()->C()...` で、内部からのみ呼ばれる特殊化（3段目以降）が生成されずリンクエラーになっていた（パス上限が2固定だった）。上限を上げて新規特殊化が尽きるまで反復する。ジェネリックなコレクション実装（TreeMapの内部ヘルパ・AVL回転等）が動くようになった
  - **コード生成の複雑度ガードの誤検出を修正**: `estimateMaxLoopDepth`（PHI数ヒューリスティック）でループ深度を掛けて複雑度を過大評価し、多数の関数を持つ正当なコード（ジェネリック展開等）を「無限ループ/過剰複雑度」と誤判定していた。ループ実行回数はコード生成コストと無関係なため乗算を撤去し、しきい値を調整（真の暴走はコード生成の30秒タイムアウトで捕捉）

### 型システム: ジェネリック特殊化の型同一性を構造化（C7/C8/C9）

大規模開発ボトルネック監査の構造的テーマ「文字列ベースの型同一性」に対する基盤リファクタリング（設計文書: `docs/archive/v0.17.0/type-identity-recursive-keys.md`）。

- **ネストした型引数（`Box<Pair<int,string>>`・`Box<Box<int>>`等）のフィールド読み書きが全バックエンドで正しく動くようになった（C7）**: 特殊化の収集・生成・参照書き換えからフラット名（`Box__Pair__int__string`）の再パースを排除し、`hir::Type`ツリー（基底名+型引数の再帰構造）を唯一の真実として走査するようにした。あわせて書き込み側のMIR lowering（左辺値構築）がフィールド型の型パラメータ置換を`kind == Generic`でしか行わず、ネストメンバへの代入文（`b.value.first = 42`）が黙って脱落していた欠陥を修正した（読み取り側と同じgeneric_params名照合へ統一）
- **ユーザー定義`Box__int`とジェネリック`Box<int>`が同一プログラムで共存できるようになった（C8）**: 特殊化シンボル名の生成を`struct_symbol_key`へ一元化し、フラット連結名がユーザー定義構造体と同名になる場合は`$`区切りの可逆エンコード名（`Box$1$3$int`。`$`はCm識別子に使えないため原理的に衝突しない）へ退避する。通常ケースは従来のフラット名を維持するため既存プログラムのシンボルは変わらない
- **`Box<T>`の`T[N]`配列フィールドのstride不一致を根絶（C9）**: 特殊化構造体のフィールドレイアウト計算を独自の手書きswitch（配列を8バイトblob扱い）から`calculate_specialized_type_size`/`calculate_specialized_type_align`（自然アライメントのCレイアウト・要素型の再帰計算）へ統合し、二重管理を廃止した
- **型キーの可逆エンコーディング`typekey`モジュールを追加**: `encode_type_key`/`decode_type_key`は長さプレフィックス付きで往復不変（`decode(encode(t))`が構造一致）。`Box<Box<int>>`・`Box<Box,int>`・ユーザー定義`Box__Box__int`のようにフラット連結では同一名へ縮退していた組が異なるキーへ分離される。ユニットテスト13ケースで固定
- **1型パラメータ基底のフラット特殊化名の復元を修正**: `Vector__Vector__int`のようなネスト特殊化名の型引数復元で、セグメントを個別引数（`[Vector, int]`）と誤解釈していた箇所を「全セグメント結合で1引数（`[Vector__int]`）」へ統一する共通ヘルパ`parse_flat_type_args`に集約した
- 回帰テスト: `tests/common/generics/nested_type_args.cm`（C7）・`box_array_field.cm`（C9）・`user_type_name_collision.cm`（C8）を追加し、jit/native/js/wasmで出力一致を確認

### 型検査: マングリング名の衝突検出（C16）

メソッド・自由関数・モジュール修飾名が同一のフラットなシンボル名へ縮退すると、従来は片方の本体が黙って上書き・消滅していた（全バックエンド共通の誤コンパイル）。設計文書: `docs/archive/v0.17.0/mangling-collision-detection.md`。

- **単一シンボルテーブルによる衝突のハードエラー化**: 型検査の宣言登録に`mangled_symbols_`（最終マングル名 → 由来・シグネチャ・宣言位置）を追加し、本体を持つ自由関数（モジュール修飾は`::`→`__`へフラット化）・implメソッド・コンストラクタ/デストラクタを登録する。別由来の同名は「シンボル '{名前}' が重複しています: {由来1} と {由来2} が同一のリンケージ名に縮退します」の診断付きコンパイルエラーになる。モジュールflattenによる同一定義の再出現（由来・シグネチャ完全一致）は従来どおり許容する
- **マングル規則を`src/internal/base/mangle.hpp`へ集約**: メソッド（`Type__method`）・ctor/dtor・`::`→`__`変換の生成規則を型検査とHIR/MIR loweringで共有し、規則複製による不一致を解消した
- 回帰テスト: `tests/common/errors/mangle_method_free_fn_collision.cm`（メソッド対自由関数）・`mangle_module_method_collision.cm`（モジュール関数対自由関数）を追加
- 注: これまで「黙って壊れていた」プログラムがコンパイルエラーになるため表面上はエラーが増えるが、従来から誤コンパイルされ正しく動いていなかったため実質的な破壊的変更ではない

### 型検査: ジェネリックインスタンス化の診断（H15/L8）

不正なインスタンス化が無診断で通過し下流の紛らわしいエラーや誤動作になっていた問題を、型検査での明確な診断に集約した。設計文書: `docs/archive/v0.17.0/generic-instantiation-diagnostics.md`。

- **型引数なしのジェネリック型宣言をエラー化**: `Pair q;` のように推論の材料が無い使用は「ジェネリック型 'Pair' には型引数が 2 個必要です」を診断する
- **存在しない型引数をエラー化**: `Pair<int, Nope>` のような未定義型名の型引数は「'Pair' の型引数に未定義の型 'Nope' が指定されています」を診断する（`is_valid_type` の型引数への再帰検証）
- **ジェネリック関数の明示型引数の個数検証**: `size_of<A, B>()` のような明示指定がパラメータ数と食い違う場合を診断する
- **境界未宣言の演算子使用を警告（L8）**: ジェネリック本体が型パラメータ値に比較演算子（`<` `<=` `>` `>=` `==` `!=`）を使っているのに境界が全く宣言されていない場合、宣言時に「型パラメータ 'T' は演算子 '<' を使用していますが、インターフェース境界が宣言されていません（<T: Ord> と宣言してください）」を警告する。既存の正当なコードはインスタンス化側の制約検査で守られているため破壊的変更回避の方針でまず警告とし、誤検出が無いことを確認した後にエラーへ昇格する
- 回帰テスト: `generic_no_args.cm`・`generic_unknown_arg.cm`（エラー期待）と `generic_bound_satisfied.cm`（回帰保護）を追加。既存 `basic_generics.cm` は境界を明記する形へ更新

### メモリ管理: ループ本体のRAII・ネストデストラクタ・move二重解放（C13/M15/H12の一部）

「メモリを解放しない」構造的テーマへの対応の第一弾（設計文書: `docs/archive/v0.17.0/memory-drop-and-lifetime.md`。C12=コンパイラ一時オブジェクトのdropパスは下記の別項で対応）。

- **while/forループ本体でRAIIデストラクタが毎周期実行されるようになった（C13）**: 従来はループ本体スコープの終了でデストラクタが走らず（`{}`で囲んだ時のみ動作）、ループ内で束縛した`Vector`等が関数終了まで無条件にリークしていた。`lower_while`/`lower_for`のボディ末尾（deferの後、明示ブロックと同一の順序規約）と、`break`/`continue`による途中脱出経路にデストラクタ実行を追加した
- **ネストしたジェネリックのデストラクタが全段まで降りるようになった（M15）**: `Vector<Vector<T>>`のデストラクタ特殊化で、要素型（`Vector<T>`）自身の特殊化デストラクタが未生成だと要素解放ループの挿入自体が見送られ、内側の要素データがリークしていた。基底のジェネリックデストラクタが存在すれば呼び出しを挿入し、単相化の不動点ループに特殊化を連鎖生成させるようにした
- **move済み変数の二重解放を修正**: `outer.push(move inner)` のように所有権を渡した変数が、スコープ終了時にもデストラクタ実行されて移動先と二重解放になっていた（上記M15対応で顕在化）。move式の変数参照をMIRへ伝搬し、moved-out変数のデストラクタ登録を解除するようにした
- **move後使用チェックのすり抜けを縮小（H12の一部）**: フィールド経由のmove（`move obj.field`）で基底変数が移動済みとしてマークされるようになり、文字列補間`{s}`内のmove後使用も診断されるようになった。診断メッセージをi18n化（「move後の変数 '{0}' を使用しています」）
- 回帰テスト: `destructor_loop_scope.cm`（C13）・`nested_generic_destructor.cm`（M15）・`move_field_then_use.cm`/`move_then_interpolate.cm`（H12、エラー期待）を追加

### バグ修正: AVX-512マスク環境での断続的SIGILL（nativeコード生成の機能否定）

CIのnative O3（ubuntu）で`parse_option_test`/`sync_basic`が特定runのみSIGILL（illegal instruction）になる断続的失敗の真因を特定し修正した。

- **真因**: nativeコード生成はホストのCPU名（`getHostCPUName`、例: `znver4`）と有効機能の加算リスト（`+avx,+avx2,...`）でターゲットを構成していたが、CPU名はそのCPUの既定機能（Zen4ならAVX-512）を**含意**する。ハイパーバイザがAVX-512をマスクしたVM（Azure EPYC 9V74の一部インスタンス。`/proc/cpuinfo`は`avx avx2`のみ）でも、機能リストに明示否定が無いためznver4既定のAVX-512命令が生成され、実行時にSIGILLになっていた。VM割り当てごとのマスク差が断続性の正体（同一CPUモデル・完全再現ビルドでもrunごとに結果が変わる）
- **修正**: clangの`-march=native`と同様に、無効な機能を`-feature`として明示的に否定する機能文字列を渡し、コード生成を実ホストの機能へ正確に一致させる
- **調査計装（残置）**: `CM_DUMP_TARGET=1`でコード生成に使うtriple/CPU名/機能文字列を出力、`CM_TARGET_CPU`/`CM_TARGET_FEATURES`でターゲットを上書き可能（特定環境向けの回避レバー）。CIの統合テストジョブはランナーCPUのfp16/amx/avx系フラグとcmのターゲットダンプをログ出力する

### 言語/バックエンド: reduce等の高階関数×クロージャ対応（C6拡張）

C6で導入したキャプチャ環境化をmap/filter以外の高階関数へ拡張した。従来`reduce`/`some`/`every`/`findIndex`/`forEach`へキャプチャ付きクロージャを渡すと、ランタイムがキャプチャ無しで`callback(acc, elem)`を呼び、ラムダ`(base, acc, x)`が2引数で呼ばれて**ガベージを返していた**（jsはbind引数のローカル名不一致でReferenceError）。

- MIRの書き換えパスをHOF全ファミリ（reduce/forEach/some/every/findIndexのi32/i64変種）へ一般化（コールバックは`args[2]`で特定。reduceは第4引数に初期値を持つため`args.back()`判定を廃止）
- native/wasmランタイムへ`void* env`を受けるクロージャ変種10関数を追加し、LLVMのサンク合成をHOFごとのレイアウト（reduce=acc+elemの2追加パラメータ、述語系=bool返し、forEach=void）へ一般化
- js/tsは全キャプチャを正順で渡す`.reduce((acc, x) => fn(caps..., acc, x), init)`等へ変換。定数畳み込みでローカル宣言が省略された変数をbindする際のReferenceErrorも修正（インライン値を直接バインド）
- テスト: `closure_multi_capture_hof.cm`へreduce（int/long）・some/every/findIndex×キャプチャを追加（jit/native/wasm/js一致）

### コンパイル時間: コード生成タイムアウトのプロセス分離（M6）

30秒のコード生成タイムアウト時にスレッドを`detach`していたため、(1) 走り続けるLLVM内部ループがGB級メモリを保持したまま残留する、(2) detach後に呼び出し元のスタックが破棄され、参照キャプチャの結果バッファへ書き込むuse-after-freeが起きる、という2つの問題があった（設計文書: `docs/archive/v0.17.0/incremental-build-and-parallel-codegen.md`のM6）。

- POSIXではforkした子プロセスでコード生成を実行し、タイムアウト・出力サイズ超過時は`SIGKILL`で計算資源ごと確実に回収する
- fork失敗時・Windowsは従来のスレッド方式へフォールバックし、共有状態を`shared_ptr`でheap化してuse-after-freeを排除
- タイムアウト秒数は`CM_CODEGEN_TIMEOUT`環境変数で上書き可能にした（既定30秒を超える大規模ビルドへの対応と、`CM_CODEGEN_TIMEOUT=0`によるタイムアウト経路そのもののE2E検証用）

### コンパイル時間: モジュール別キャッシュと並列コード生成（H14、実験的）

コード生成が単一スレッド・キャッシュ無しで関数数に対し超線形だったため、死蔵していたモジュール分割コンパイル経路（`compileModules`+`linkObjects`）をドライバへ接続した（設計文書: `docs/archive/v0.17.0/incremental-build-and-parallel-codegen.md`のH14）。

- `CM_MODULE_CODEGEN=1`（実験ゲート）でnative実行形式のコンパイルがモジュール分割経路になる。モジュールごとにMIR内容ハッシュ（関数全文+extern関数全文+全型レイアウト+ターゲット/最適化設定）を計算し、`.tmp/module-cache/<モジュール>-<ハッシュ>.o`が既にあればコード生成・最適化を丸ごとスキップする（内容アドレス方式のためフロントエンド差分検知なしで正確）
- キャッシュミスしたモジュールは独立`LLVMContext`のワーカスレッドで並列コンパイルする（ワーカ数は`CM_CODEGEN_JOBS`で上書き可能）。ワーカからのforkはmallocロック競合でデッドロックしうるため、モジュール.oのemitはfork分離なしの直接版を使う
- vtable（動的ディスパッチ）は分割元プログラム参照経由の全関数宣言解決で分割経路に対応（vtable配列はモジュールごとのPrivateLinkage複製だが、エントリはExternalLinkage関数参照でfat pointer間接呼び出しはモジュール境界を越えて正しく動作）。サニタイザ有効時・非native・実行形式以外の出力は従来の全体コンパイルへ自動フォールバックする
- 死蔵経路の接続で発覚した8クラスの不具合を修正: (1) モノモーフ化特殊化の擬似ソース名`<generated>`がそのまま.oファイル名・シェルコマンドに入り壊れる (2) body付きextern関数（Bug#45経路）が定義元モジュールと重複定義になりO0でリンクエラー・O2で不整合な実体が残る（`linkonce_odr`化で解消） (3) ローカル変数走査による型参照収集がフィールド経由・自己参照ポインタを見落とし、未登録の構造体名がタグ付きユニオン互換のフォールバックレイアウト（`{i32, i8[8]}`）へ落ちてモジュール間でGEPオフセットが食い違いSIGSEGV（全型定義を全モジュールへ配布して解消） (4) グローバル変数が全モジュールへ複製定義され初期化状態が分裂（所有モジュール一本化+他はextern宣言で解消） (5) リンク時のランタイムライブラリ要否判定が空のリンク用モジュールを見て常にfalseになりnet/sync/thread系がリンク失敗（MIRの呼び出し関数名から判定するよう変更。HTTPランタイムのOpenSSLリンクフラグ欠落も補完） (6) モジュール変換が`currentProgram`未設定のままモジュール修飾呼び出し（`m::calculate`等）の存在判定へ入りコンパイラ自身がSIGSEGV（分割元プログラム参照`origin`を導入） (7) extern関数の参照収集漏れ（Call terminator直参照以外）で`declareExternalFunction`フォールバックが誤ったシグネチャを推測し、構造体値渡しABIが崩れて壊れた値が出る（全関数のMIRシグネチャを各モジュールへ宣言して根絶） (8) キャッシュキーがコンパイラ自身の変更を含まず、コンパイラ更新後も古い.oを再利用してしまう（実行バイナリのパス+サイズ+更新時刻をキーへ混入）

### 生成物サイズ: ジェネリック特殊化の同一コード折り畳み（M10）

### メモリ管理: スライス一時のdropパス（C12のスライス一時）

文単位一時dropパス（C12の文字列一時）をスライスへ拡張した。`map`/`filter`が返す無名の中間スライス（ヘッダ+データを所有）はどこからも解放されず、ループ内の`xs.map(f)[0]`のような式が反復回数に比例してリークしていた。

- `__builtin_array_map*`/`__builtin_array_filter*`の結果一時を文スコープへ登録し、既存のエスケープ解析（let束縛・格納・ユーザー関数への引き渡しは解放しない）を共用して非エスケープ一時へ`cm_slice_free`を発行する
- スライスの読み取り系（`cm_slice_get_*`/`len`/`first`/`last`）と高階関数（チェーンの中間入力）を非保持ホワイトリストへ追加。格納系（`cm_slice_push_*`）はエスケープ扱いのまま
- js/tsはGC管理のためno-op、SVは黙ってスキップ（文字列一時と同じ扱い）
- 実測: `xs.map(add1)[0]`を100万回繰り返すループで最大RSSが65.6MB（線形リーク）→1.4MB（平坦）
- テスト: `tests/common/memory/temp_slice_drop.cm`（読み出し消費・let束縛エスケープ・チェーン中間・ループ内一時、全バックエンド一致）・`mir_lowering_test`（式文で解放・let束縛で非解放のMIR検査）

### メモリ管理: 条件腕内一時のdropパス（C12の条件式内一時）

三項演算子・短絡評価の腕で確保される一時は、文末の解放地点では未初期化ポインタをfreeする危険があるため一律に解放対象外で、腕内の連結・変換一時がループでリークしていた。

- 腕ごとの一時スコープ（`ArmTempScope`）を導入し、腕内で確保され腕内で完結する一時を腕ブロック内（mergeへの分岐前）でエスケープ解析して解放する。選ばれなかった腕の一時は評価自体が起きないため未初期化freeは構造的に発生しない
- 腕の結果値（`result = copy(値)`）はUseエスケープとして既存の解析で自然に保護され、ユーザー関数へ渡った一時・ネストした三項の腕も同じ規則で扱う

- テスト: `tests/common/memory/conditional_arm_temp_drop.cm`（腕内完結・短絡右辺・結果エスケープ・関数引き渡し・ネスト三項、全バックエンド一致）

### 言語: 文字列len()のUTF-8コードポイント化とbyte_len()の追加（H9第2段・第3段）

文字列の`len()`はNUL終端バイト数（jsはUTF-16単位）で、マルチバイト文字列の「文字数」が取得できず、バックエンド間でも意味が食い違っていた（設計文書: `docs/archive/v0.17.0/strings-utf8-and-stringbuilder.md`）。

- **`len()`をUTF-8コードポイント数へ変更**: native/wasmは継続バイト（0b10xxxxxx）を数えないO(n)スキャン、jsは`[...s].length`（サロゲートペア=絵文字も1と数える）。`"こんにちは".len()`は5、`"😀🚀".len()`は2
- **`byte_len()`を追加**: UTF-8バイト数を返す（`"こんにちは".byte_len()`は15）。jsは`TextEncoder.encode(s).length`でUTF-8バイト数を返す（従来の`.length`はUTF-16単位でnativeと不一致だった）
- **破壊的変更の範囲**: ASCIIのみの文字列は`len()==byte_len()`で挙動不変。マルチバイト文字列で`len()`をバイト数として使っていたコードは`byte_len()`へ移行が必要
- **`substring()`/`slice()`の添字をコードポイント単位へ統一**: 従来はnative=バイト・js=UTF-16単位で意味が食い違い、マルチバイト文字の途中で切れて壊れたUTF-8を生んでいた。負添字のPython風意味論（末尾からの位置）は維持。`"a😀b漢c".substring(1, 2)`は`"😀"`
- **`codepoint_at(i)`を追加**: コードポイント添字`i`のUnicodeスカラ値を`uint`で返す（`"あ".codepoint_at(0)`は12354、範囲外は0）
- **`chars()`を追加**: コードポイント列を`uint[]`スライスで返し、`for (cp in s.chars())`で列挙できる（native/wasm=UTF-8デコード+スライス構築、js=スプレッド+codePointAt。結果スライスはC12のdropパス対象）
- **`indexOf()`の戻り値をコードポイント添字へ統一**: 従来はnative=バイトオフセット・js=UTF-16単位で不一致だった（`"あいうえお".indexOf("うえ")`は2、未検出は-1のまま）
- `charAt()`/`at()`はバイト単位のアクセスとして維持（`byte_len()`と対のバイトAPI）。SVは文字列長が静的解決のため対象外
- テスト: `tests/common/strings/utf8_len_test.cm`（長さ）・`utf8_index_test.cm`（部分文字列・codepoint_at）・`utf8_chars_test.cm`（chars()列挙・indexOfコードポイント添字）をjit/native/wasm/js/tsで検証。チュートリアル`docs/tutorials/{ja,en}/stdlib/strings/length.md`を新設

### 標準ライブラリ: StringBuilder（H9第1段）

ループ内の文字列連結 `s = s + "..."` は毎回全体をコピーするためO(n²)で、N=200kで数秒かかっていた（設計文書: `docs/archive/v0.17.0/strings-utf8-and-stringbuilder.md`のH9。第1段=表現非依存のStringBuilder先行導入）。

### メモリ管理: 三項結果一時のdropパス（C12の条件式内一時の完結）

三項演算子の結果一時は腕の値の所有権が条件依存（fresh一時か借用かが実行時に決まる）のため一律に解放対象外で、`(cond ? a+"x" : b+"y").len()`のような消費のみの式がループでリークしていた。

- 所有権判定付きの腕スコープ終了を導入: 腕の値が腕内登録のfresh一時で、腕内での使用が読み取り・非保持呼び出しと結果ローカルへのUseコピー1回だけの場合、「所有権が結果へ移動した」と判定する
- 両腕がともに同種（文字列同士・スライス同士）の所有権移動をした場合のみ、結果一時を外側スコープ（文または外側の腕）の所有一時として登録し、既存のエスケープ解析で非エスケープなら解放する。どちらの実行経路でも結果はfresh所有バッファなので未初期化・二重解放は構造的に起きない
- 片腕でも借用値（変数コピー・リテラル）の場合は登録せず、借用元の値の健全性を保つ（`cond ? s1 : a+b`のs1は生き続ける）
- 実測: 三項腕連結の消費100万回ループで最大RSSが17.4MB（線形リーク）→1.4MB（平坦）
- テスト: `tests/common/memory/ternary_result_temp_drop.cm`（両腕fresh消費・片腕借用の健全性・letエスケープ・関数引き渡し・ネスト三項、全バックエンド一致）

### メモリ管理: 文字列再代入時の旧バッファ解放（C12の変数上書き）

`s = s + "x"` のような文字列ローカルの再代入は旧バッファを解放せず、ループで線形にリークしていた。

- MIRパス`StringReassignFree`（O1以上・最適化パイプライン先頭）を追加し、(1) 全定義がfresh所有バッファ（`cm_string_concat`・`cm_*_to_string`等の結果の単独消費一時） (2) エイリアスされない（コピー先一時のプロファイルを1段追跡し、`println`等の引数一時経由の読み取りは許容） (3) 到達定義解析で未初期化・リテラルが混ざらない、の3条件を満たすローカルに限り、再代入直前へ旧値の`cm_string_free`を挿入する
- リテラル初期化のアキュムレータ（`string acc = "";`）は到達定義にリテラルが混ざるため保守的にスキップ（リテラルのfreeは即クラッシュ）。他変数へコピーされた（エイリアスされた）変数もスキップし、use-after-freeを構造的に排除する
- freshバッファ同士は生存期間が重なる別mallocのため旧値と新値のポインタ一致は起きず、挿入位置は定義文の直前（RHSの読み取り完了後）のため解放後の読みも発生しない。収束マネージャによる再実行は退避ローカルの冪等性ガードで二重挿入を防ぐ
- 実測: fresh再代入の100万回ループで最大RSSが33.5MB（線形リーク）→1.3MB（平坦）
- テスト: `tests/unit/mir_pass_test.cpp`（fresh再代入で解放・リテラル初期化とエイリアスはスキップの3ケース）・`tests/common/memory/string_reassign_drop.cm`（全バックエンド一致・値の健全性）

### 診断: リンク長時間化の切り分け警告

ネイティブ実行形式のリンクは`std::system`によるシステムリンカ（clang++/ld）の子プロセス待ちであり、セキュリティソフトが新規生成バイナリをスキャンする環境ではリンクが分単位でブロックされ、cmがハングしたように見える事象があった（実調査ではESETのリアルタイム保護+macOSのsyspolicyd評価が原因で、cm自身は`__wait4`で子プロセスを待機していた）。
リンク実行が10秒を超えた場合に「cmはシステムリンカを待機しており、セキュリティソフトの新規バイナリスキャンが原因になりうる」旨の警告をstderrへ出すようにし、同事象の切り分けを即座に行えるようにした（`emitExecutable`と`linkObjects`の両リンク経路）。

### バグ修正: ジェネリック配列フィールドの要素型伝播とLinuxでの選択import解決

- **`ArrBox<short>`等のジェネリック構造体の配列フィールド要素アクセスで、単相化の型伝播パスが要素destの型を未置換の`T[4]`で上書きしていた問題を修正**: `bs.items[i]`のMIR一時はloweringが正しい要素型（short等）を付けるが、mono_structsのフィールドアクセス型更新がIndex射影で打ち切ってフィールドの配列型をそのまま採用し、LLVMに`[4 x %T]`（12バイトstride）のallocaが生成されてスタック隣接領域を壊していた（JIT O0でのみ顕在化し、スタック配置の違いでubuntu CIだけ壊れてmacOSは偶然通っていた）。Index射影で要素型へ降下し、`T[N]`フィールドの要素型パラメータ置換も追加。解決できない射影（Deref等）ではloweringの型を維持して上書きしない

- デバッグ支援: `CM_DUMP_IR=1`でJIT実行直前のLLVM IRをstderrへダンプできるようにした（プラットフォーム差の調査用）

### JS/TS: 構造体の関数引数を値渡しに統一（H3）

js/tsだけ構造体の関数引数が参照渡しで、呼び出し先での変更が呼び出し元へ漏れてLLVM系（値渡しで隔離）と意味論が分裂していた（let束縛とreturnは`__cm_clone`するのに実引数だけクローンされなかった。設計文書: `docs/archive/v0.17.0/js-ts-value-semantics.md`）。

- 関数呼び出しの実引数生成で、構造体のCopy引数を`__cm_clone`で深いコピーにして値渡しへ統一した
- クローン対象外（参照渡しを維持）: implメソッドのself（第1引数、変更を呼び出し元へ伝搬させる既存意味論）・仮想ディスパッチのレシーバ・インターフェイス値・外部JSオブジェクト（関数型フィールド構造体）・ランタイム組み込みへの引数（`indexOf`/`includes`等はJSのオブジェクト同一性比較に依存するため）
- H5（long/ulongのBigInt化）は波及範囲が広くTypeErrorリスクが高いため段階計画のまま未着手
- テスト: `tests/common/functions/struct_arg_value_semantics.cm`（同一変数の2回渡しの隔離・implメソッドself伝搬の非退行、全バックエンド一致）

### 型システム: 集約に入るインターフェイス値のfat pointer構築（H1/H2）

インターフェイス値のfat pointer（データ+vtable）構築が「射影なしのローカル代入」経路にしか無く、構造体フィールド・配列・スライスへ具象構造体を格納すると生値がそのまま入り、動的ディスパッチが不正なvtableを読んでnative/jit/wasmクラッシュ・jsでvtable undefinedになっていた（設計文書: `docs/archive/v0.17.0/interface-values-in-aggregates.md`）。ポリモーフィックコレクションが使えるようになった。

- **射影付きplaceへのcoercion（H2）**: LLVMのassignに、格納先の静的型（Field射影は構造体定義・Index/Derefは要素型で解決）がインターフェイスなら具象構造体からfat pointerを構築してstoreする経路を追加。JSも同様に`{data, vtable}`を構築する。`Box{sh: sq}`のリテラル初期化・`b.sh = sq2`のフィールド代入・`shapes[1] = sq6`の要素上書きが全て動作する
- **インターフェイススライス（H1）**: `layout_size`がインターフェイス値をfat pointer幅（ポインタ2個分、wasm32は8バイト）で計算するようにし、スライスリテラル・`push`では具象値をインターフェイス型の一時へ代入してfat構築してからblob格納する。`Shape[] list = [sq, ci]; list.push(ci3);`と添字読み出し+動的ディスパッチが動作する
- **補間内の配列要素メソッド呼び出しの黙殺を解消**: 補間ミニパイプラインは型チェッカーを通らず添字式の結果型が未設定のため、受信型が`<error>`になり`__error__area`等の未定義シンボルへ黙って解決されリンク失敗していた（インターフェイスに限らず構造体配列全般）。`lower_index`が基底の型から要素型を導出するようにした
- テスト: `tests/common/interface/interface_in_aggregates.cm`（フィールド・固定長配列・スライス・push・補間・混在具象型・ループディスパッチ、jit/native/wasm/js一致）・`tests/common/basic/interp_array_method.cm`（補間内の配列要素メソッド）

### モジュール: 選択importの重複排除と型名itemの解決（M7）

`import std::collections::Vector;`が「Duplicate method: Vector<T> already has method 'push'」で失敗する問題を修正した（設計文書: `docs/archive/v0.17.0/module-visibility-and-import-dedup.md`のM7）。真因は3点が重なっていた。

- **大文字開始の末尾セグメント（型名）がimportのitemとして解釈されない**: 小文字のみitem扱いのヒューリスティックのため`Vector`がモジュールパス扱いになり、大小文字を区別しないファイルシステム（macOS等）では`Vector.cm`が`vector.cm`へ誤解決され、`namespace Vector`と`struct Vector`が衝突していた（Linuxでは解決失敗エラーでプラットフォーム差もあった）。モジュールとして解決できない/大小文字違いでのみ一致する場合は親モジュールからの選択import（`std::collections::{Vector}`）として再解釈する
- **同一ファイルからの2回目以降の選択importが本体を再出力**: `import std::collections::Vector; import std::collections::Queue;`のような連続選択importで、展開済みのネストimport領域・非export型・implが再出力されDuplicate methodになっていた。`filter_exports`に増分モードを追加し、2回目以降は新規要求シンボルのブロックだけを出力する
- **`export import`（再export）構文が未処理**: `mod.cm`の`export import std.collections.vector;`が展開されず、mod.cm経由の選択importは本体を一切取り込めなかった。ワイルドカード相当として展開するようにした（`import std::collections::{Vector, Queue}`のブレース形式も動作する）。選択的再export（`export import x::{items}`、io形式）はMIR組み込みのprintln等をCm定義で影に置き換えて挙動を変えるため従来どおり展開しない
- テスト: `tests/common/modules/selective_import_dedup.cm`（型名の選択import・連続選択import・間接importの共存をjit/native/wasmで検証）

### 型検査: const集約への深い代入の警告（M3の段階導入）

`const Point p = ...; p.x = 99;` のようなconst構造体のフィールド代入・const配列の要素代入が`--strict`でも検出されず実行されていた（constが集約に対して浅い）。既存コードが浅いconstに依存しているため即エラー化は破壊的変更となることから、check/lint時の警告として段階導入した（設計文書: `docs/archive/v0.17.0/const-aggregate-enforcement.md`、段階3のconstポインタ化警告まで完了しarchiveへ移動。エラー化は将来のバージョンで実施）。

### 言語/バックエンド: 複数キャプチャクロージャの高階関数対応（C6）

`map`/`filter`へ渡すクロージャのキャプチャをランタイムが単一スカラ（native=int64/wasm=int32で幅も不一致）で受けていたため、2変数以上キャプチャするクロージャはnative/jit/wasmでLLVM検証エラーになり、js/tsは2個目以降のキャプチャを黙って落として誤答し、引数順も逆で非可換演算は単一キャプチャでも誤答だった（設計文書: `docs/archive/v0.17.0/closures-multi-capture.md`）。

- **キャプチャ環境ポインタ方式へ統一**: ランタイムのクロージャ関数型を`fn(void* env, elem)`へ変更し（native/wasm両方、幅不一致も解消）、LLVMコード生成が呼び出し点でキャプチャ列をスタック上のi64スロット配列（関数エントリのalloca）へ格納し、環境からキャプチャを復元してラムダを呼ぶサンク関数を合成して`[配列, サイズ, サンク, env]`の固定4引数へ正規化する。キャプチャ数に依存しないシグネチャになり、整数幅・ポインタ・浮動小数のキャプチャを可逆に往復する
- **js/tsのキャプチャ落ちと引数順を修正**: 生成ラムダのパラメータは[キャプチャ..., 要素]の並びに対し、従来は先頭キャプチャ1個だけを要素の後ろに渡していた（減算等の非可換演算は単一キャプチャでも誤答）。全キャプチャを正順で渡すよう修正し、`_i64_closure`変種の対応漏れも追加
- **long要素のmap/filterディスパッチ欠落を修正**: 要素型を見ずに常時i32版ランタイムが選ばれ、`long[]`のmap/filterがstride不一致で黙って壊れていた（キャプチャ無しでも誤答）。64bit整数要素は`_i64`変種を選ぶようにし、非クロージャ版`map_i64`/`filter_i64`のLLVM宣言欠落も追加
- 既知の残課題: `reduce`等のmap/filter以外の高階関数×クロージャは未対応（native/jit/wasmはランタイム実体が無く宣言エラー、jsはbind引数のローカル名不一致でReferenceErrorと、いずれも黙殺ではなく音を立てて失敗する）
- テスト: `tests/common/array_higher_order/closure_multi_capture_hof.cm`（2/3キャプチャのmap・2キャプチャのfilter・非可換演算の引数順・long要素・ループ内mapを全バックエンドで検証）

### メモリ管理: 文単位の一時文字列dropパス（C12の文字列一時）

コンパイラが生成する無名の一時文字列（`+`連結・数値→文字列変換・文字列補間の脱糖結果）は全バックエンドで一切解放されず、ループ内の文字列連結が反復回数に比例してリークしていた（`cm_string_free`相当の呼び出し箇所ゼロ）。MIR loweringに文単位の一時トラッキングを導入し、文の評価完了後にエスケープしなかった一時へ`cm_string_free`呼び出しを発行するようにした（設計文書: `docs/archive/v0.17.0/memory-drop-and-lifetime.md` Phase 3）。

- **対象は単純文（let・代入・式文）のコンパイラ生成文字列一時**: `cm_string_concat`と`cm_*_to_string`の結果を文スコープへ登録し、文のMIR範囲をスキャンするエスケープ解析で所有権の移動を判定する。読み取りのみの使用（`println`等の出力系・`len`等の`__builtin_string_*`・比較・さらなる連結の入力）は解放対象のまま、let束縛・代入・ユーザー関数への引き渡し・コンテナ格納・集約構築・参照化・returnはエスケープ扱いで解放しない
- **条件付き実行の腕は追跡対象外**: 三項演算子の腕・短絡評価（`&&`/`||`）の右辺で確保される一時は、文末の解放地点で未初期化ポインタをfreeする危険があるため登録を抑止する（従来どおりリークするが安全側）
- **ランタイム**: `cm_string_free`をnative/wasm両ランタイムへ追加（NULL無視）。wasmはH11のフリーリストアロケータにより実メモリが再利用される。js/tsはGC管理のためno-op、SVバックエンドは解放呼び出しを黙ってスキップする
- 実測: 40文字文字列の`(a + "x").len()`を200万回繰り返すループで最大RSSが97.8MB（線形リーク）→1.4MB（平坦）
- 既知の制限: `s = s + "x"`で上書きされた変数の旧バッファ、if/while条件式内の一時、ユーザー関数へ渡した一時は未解放（段階的に拡張する）
- テスト: `tests/common/memory/temp_string_drop.cm`（解放対象と非対象の健全性・全バックエンド）・`tests/common/collections/temp_string_push_escape.cm`（コンテナ格納のエスケープ）・`tests/regression/mir_lowering_test.cpp`（式文で解放・let束縛で非解放・三項演算子の腕で非解放のMIR検査）

### コンパイル時間・型システム: 大構造体戻り値のsret化と値渡し引数の隔離修正（C14 Phase 4）

16バイト超構造体の戻り値は第一級集約returnとして生成され、SROAが全要素展開するため`int[16384]`フィールド構造体を返す関数はO2で60秒超タイムアウトしていた（設計文書: `docs/archive/v0.17.0/aggregate-copy-lowering.md`のPhase 4）。

- **sret変換**: 非extern・非アドレス取得関数で戻り値が16バイト超構造体の場合、シグネチャを「戻り値void+先頭に隠し出力ポインタ（sret/noalias属性付き）」へ変換。関数本体はReturn時にretval allocaから呼び出し元バッファへmemcpy、呼び出し側は格納先allocaを直接渡すため戻り値のstore/memcpyが消える（コピー0回）。実測で`int[16384]`戻り値のO2コンパイルが60秒超→0.6秒
- **除外条件**: extern関数（FFI ABI互換）・アドレス取得された関数（関数ポインタ・vtable経由の間接呼び出しはシグネチャ変換を追跡できないためMIR全体走査で検出）・インターフェイス値（fat pointer16バイト）・main
- **付随修正3件**: (1) `isSmallStruct`がArrayフィールドをdefault 8バイトと誤計算し大配列構造体を「小」と誤判定→サイズ判定をLLVM DataLayoutの正確な値へ (2) Bug#45の引数個数チェックがsret関数（パラメータ=引数+1）を不正と誤判定しcalleeを破棄→sret考慮の+1補正 (3) **16バイト超構造体のポインタ渡し引数を呼び出し先が変更すると呼び出し元の値へ波及する既存の値セマンティクスバグ**（旧版でも再現、jsはH3で分離済みでバックエンド分裂していた）→byval相当のエントリコピー（alloca+memcpy）で隔離。implメソッドのselfはMIR型がPointerのため従来どおり参照渡し
- **大配列構造体の値渡し引数も統一**: `isSmallStruct`をDataLayoutの正確なサイズ判定へ修正し、Arrayフィールド8バイト誤計算で第一級集約渡しになっていた大配列構造体引数（`int[16384]`引数でwasm Ozが145秒）もポインタ渡し+呼び出し先エントリコピーへ（実測0.1秒、値渡し隔離も正しく動作）
- LLVMの`byval`属性は「呼び出し側コピー」の意味論で本実装の呼び出し先コピー方式と不一致のため付与しない判断で確定（C14は全Phase完了）
- テスト: `tests/common/structs/big_struct_return.cm`（`int[16384]`戻り値の値保存・大配列引数の爆発なし+値渡し隔離・中型構造体の値渡し隔離・結果破棄のダミーバッファ経路・小構造体の従来ABI、jit/native/wasm一致）

### メモリ管理: 解放可能なwasmアロケータ（H11/M14の一部）

wasmランタイムのアロケータを、解放不可能な単調バンプから8バイトヘッダ+サイズクラス別フリーリストへ置き換えた（設計文書: `docs/archive/v0.17.0/allocator-and-temp-pool.md`）。

- **`free`/`cm_free`が実際にブロックを返却し、解放済みブロックが再利用されるようになった**: 従来は論理的に解放しても実メモリが返らず、長時間実行プログラムは総確保量に比例して線形メモリが増え続けた。確保はフリーリスト→初期64KBプール→`memory.grow`の順で行い、生存中の割り当てを上書きしない性質は維持する。ヘッダのマジック検証により、ヒープ由来でないポインタ（文字列リテラル・スタック）のfreeや二重解放は安全に無視される

- デッドインフラだった`CmTempStringPool`（呼び出し箇所ゼロ）を撤去（M14の一部）
- 回帰テスト: `tests/common/allocator/wasm_free_reuse.cm`（確保・解放・拡張の反復でデータ破壊が無いこと）

### メモリ管理: アロケータ差し替えのCmからの到達可能化とstd::mem確保経路の一本化（M14完結）

`cm_set_allocator`系APIがCmコードから到達不能で、`std::mem`がlibc mallocをFFI直呼びしていたため、アロケータを差し替えても標準ライブラリの確保に反映されなかった（設計文書: `docs/archive/v0.17.0/allocator-and-temp-pool.md`）。

- **`std::mem::set_allocator_fns(alloc_fn, dealloc_fn, realloc_fn)` / `reset_allocator()` を追加**: Cm関数ポインタ3本（`void*(long)` / `void(void*)` / `void*(void*, long)`）でグローバルアロケータを差し替え、`reset_allocator()`で既定へ戻す。CmのトップレベルfunctionはC ABI互換で生成されるため、そのまま関数ポインタとして登録できる
- **`std::mem`の確保経路を`cm_mem_alloc`/`cm_mem_dealloc`/`cm_mem_realloc`ラッパ経由へ一本化**: `alloc`/`dealloc`/`DefaultAllocator`のlibc直呼びを廃し、登録したカスタムアロケータが`std::mem`経由の全確保に反映されるようにした。`cm_alloc`系はstatic inlineで外部シンボルを持たないため、非inlineのエクスポートラッパを新設しJITのホストプロセスシンボル解決にも対応
- **対応範囲**: JIT/Nativeで差し替え有効。wasmは独自フリーリストアロケータ固定のためファサードはno-op（`cm_mem_*`はwasmランタイムへ委譲）、js/tsはGC管理のため`alloc`はダミーオブジェクト返却で対象外
- interface値渡しの`set_allocator(a)`形式はH1/H2のinterface値基盤を使う将来拡張とし、関数ポインタ形式で到達可能化を先行完結した
- 回帰テスト: `tests/common/allocator/set_allocator_facade.cm`（カウンタアロケータで`std::mem::alloc`の経由を観測し、`reset_allocator`後は加算されないことを確認。JIT/Native）

### 標準ライブラリ: OS連携モジュール（セルフホスト準備 第1段）

コンパイラのようなCLIツール（ファイルを読み、解析し、成果物を書き、外部コマンドを呼ぶプログラム）をCmで書くためのOS連携APIを整備した（設計文書: `docs/archive/v0.17.0/self-hosting-preparation.md` 第1段。libc FFIと純Cmのみで完結し、ランタイムC改修なし）。

- **std::env（新設）**: `get(name)`（`Option<string>`返し）/ `set(name, value)`。libc getenv/setenvの薄いラッパで、getは環境領域を借用しない所有コピーを返す。Native/JITのみ
- **std::process（新設）**: `run(cmd)`（systemの終了コード、WEXITSTATUS相当）/ `output(cmd)`（popen/fgetsで標準出力をStringBuilder収集、`Result<string, string>`返し）。Native/JITのみ
- **std::path（新設・純Cm）**: `join` / `dirname` / `basename` / `extension` / `with_extension`。区切りは/固定、ビルトインのindexOf/substringのみで実装しFFI不使用
- **std::bytes（新設・純Cm）**: `push_u16_le/u32_le/u64_le`とBE版、対応する`read_*`。シフトとマスクのみのエンディアン指定バイト詰め。64ビットread/writeはJSの53bit精度のため非対応
- **std::strings::split / lines（追加・純Cm）**: 空要素保持の分割・空セパレータのコードポイント分割・\r\n正規化と末尾空要素除去の行分割
- **std::fs拡張**: `create_dir(path)`（mkdir 0755）/ `remove_dir(path)`（rmdir）
- 名前空間形式import（`env::get(...)`）はモジュールシステム全体で未対応のため、選択的import＋アイテムエイリアス（`import std::env::{get as env_get}`）で使用する
- テスト: `tests/common/strings/split_lines_test.cm`・`tests/common/path/path_ops_test.cm`・`tests/common/bytes/bytes_endian_test.cm`（純Cm3本は全バックエンド）、`tests/common/env/env_get_set_test.cm`・`tests/common/process/process_run_output_test.cm`・`tests/common/fs/dir_create_remove_test.cm`（Native/JIT）

### JS/TS: long/ulongのBigInt表現化（H5、監査全所見完了）

js/tsのlong/ulongがNumber（64bit浮動小数点）表現のため、2^53超の64bit ID・タイムスタンプが黙って精度を失っていた（9223372036854775807が...776000へ丸まる）。実行時表現をBigIntへ全面移行した。

- **リテラル**は`123n`形式、**算術・ビット演算・シフト**は`BigInt.asIntN/asUintN(64)`でLLVM系の64bitラップへ一致、**除算**はBigIntのゼロ方向切り捨てでsdiv/srem一致（従来のNumber除算は小数が出てnativeと分裂していた）
- **比較**は両辺を64bit幅へ符号再解釈して===比較（ulongで-1リテラルが18446744073709551615と等価になるLLVM挙動へ一致）
- **Number混在の吸収**: `len()`等の32bit系戻り値との演算は冪等ヘルパー`__cm_big`/`__cm_trunc`で変換し、呼び出し境界（Cm関数の仮引数型・スライスpush/setのスロット幅）で明示変換を挿入してTypeErrorを構造的に排除
- **キャスト**は`asIntN/asUintN(幅)`で正確に縮小、**出力**は`String(BigInt)`で整形、**TS注釈**は`bigint`（tscターゲットes2020）。union実行時型検査・sort比較子・文字列添字ヘルパーもBigInt対応
- 従来jsスキップだった`ulong_large_hex`・`bytes_endian`（64bit往復）は**スキップ解除で全緑**
- 回帰テスト: `tests/common/types/long_bigint_precision.cm`（2^53超精度・ラップ・混在演算・キャスト・比較。jit/native/wasm/js/tsの5系一致）

### 文字列: 長さヘッダ付き文字列によるO(1)バイト長と埋め込みNUL対応（H9第4段、H9完結）

文字列がNUL終端char*のみで長さがO(n)のstrlen依存・埋め込みNUL（0x00）でデータ喪失という監査所見に対し、(ptr,len)への全面ABI変更ではなく**char*完全互換のSDS方式**（データ直前の16バイト隠しヘッダ{magic, byte_len, magic2, 確保オフセット}）で対応した。

- **リテラルもヘッダ付き**: コード生成が{ヘッダ+データ}のグローバル定数として発行しデータ先頭を参照。ランタイム生成文字列（concat/整形/substring/StringBuilder等）は全プロデューサがヘッダ付き確保へ移行
- **byte_len()がO(1)**、len()/substring/codepoint_at/連結はバイト長境界で動作し埋め込みNULを保持する
- **std::strings::from_bytes(utiny[]) を新設**: バイト列から文字列を構築（NUL含みバイト列も第一級。jsはTextDecoder写像）
- **FFI互換**: データはNUL終端char*のままなのでlibc・外部Cへゼロコストで渡せる。FFI由来のヘッダ無し文字列はstrlenへ自動フォールバック
- **安全設計**: 未知ポインタの前方読みは16バイト整列+ページ先頭ゲートで保護、確保時のページ先頭シフト（オフセットをヘッダへ記録）、解放時のマジック消去で再利用誤認を防止。二重マジック+終端検証で誤判定は実質ゼロ。MallocScribble下の反復・O0/O3・全12スイート2周で安定確認
- 回帰テスト: `tests/common/strings/embedded_nul_test.cm`（from_bytesでのNUL構築・byte_len/len/codepoint_at/substring/連結の保持。jit/native/wasm/js一致）。これによりH9は全5段完了、strings-utf8-and-stringbuilder.mdをarchiveへ移動

### バックエンド統一: double出力の最短round-trip化とfloat→intキャストの飽和（M8/M9）

同一プログラムの数値出力・キャスト結果がバックエンドで分裂していた問題を統一した（設計文書: `docs/archive/v0.17.0/numeric-output-and-cast-consistency.md`）。

### 型検査: 確定代入のフロー考慮とreturn網羅の警告（H6/L4の一部）

### バグ修正: 大規模開発ボトルネック監査で検出したスライス・型・バックエンドの不具合

大規模開発ボトルネック監査（`docs/archive/v0.17.0/large-scale-bottleneck-audit.md`）で「検証済み」とされた設計上の不具合のうち、局所修正で被害の大きいものと構造的テーマの一部を修正した。

- **`short[]`/`ushort[]` スライスがヒープ破壊する問題を修正（C4）**: 要素サイズは2バイトで確保されるのに push/get/pop が2バイト幅の関数を持たず4バイト関数へフォールバックしていたため、stride不一致で隣接要素を破壊していた（native SIGSEGV、jit/wasmでデータ破損）。2バイト幅のランタイム関数（`cm_slice_push_i16`等）を native/wasm/js に追加し、要素型→アクセス幅の選択を全経路で2バイトへ揃えた。固定長配列→スライス変換のサイズ表でも short/ushort が欠落していたのを解消
- **要素サイズ選択の一元化（構造的リファクタリング）**: 要素型→elem_size・ランタイム関数幅・ソートサフィックスの対応表が lowering の6箇所（push/pop/get選択・elem_size計算）に個別複製され、ケース漏れが上記のstride破壊を招いていた。`slice_dispatch.hpp` の `slice_scalar_info()` に集約し、elem_sizeとアクセス幅が常に一致することを1箇所で保証した（新しいスカラ型の追加も1箇所で済む）。あわせて `isize`/`usize` スライスが4バイト確保のまま8バイトアクセスされる潜在不整合も解消した
- **`slice.sort()` がint以外の要素型でゴミを返す問題を修正（C5）**: elem_size==4のときだけ実ソートし long/double/short 等は破損値を返していた。要素型ごとに符号・浮動小数・文字列を正しく比較するソート関数（`cm_slice_sort_i64`/`_f64`/`_str` 等）へディスパッチするようにし、全要素型で正しく整列する
- **メンバスライスの `pop`/`delete`/`clear` が黙って欠落する問題を修正（C11）**: レシーバが構造体メンバ（`self.items` 等）のとき変数参照しか解決せず文が丸ごと落ちていた（push のみ修正済みだった）。`get_member_place` でメンバの場所を解決するようにし、解決失敗時は黙殺せず診断を出すようにした
- **文字列の `<` `>` `<=` `>=` がアドレス比較になる問題を修正（C2）**: 比較演算子に文字列内容比較（`cm_strcmp`）の分岐が無く、結果がメモリレイアウト依存で非決定的だった。オペランドのCm型が string/cstring のときだけ内容比較へ倒すようにした（`int*` 等のポインタ順序比較はアドレス比較のまま維持）。これにより `with Ord` のstringフィールド比較も内容比較になる（C3）
- **数値→string の `as` キャストがクラッシュする問題を修正（C10）**: `2 as string` が型検査を通過し jit/native=SIGSEGV・wasm=空文字・js/ts=正常と5分裂していた。数値スカラ→string の `as` を型検査で拒否する（ユニオン downcast やポインタ→string の正当なキャストは維持）
- **WASMの `println(double/float)` が小数部を切り捨てる問題を修正（C15）**: `(int)value` で整数化するスタブのままだったのを、文字列補間と同じ `cm_format_double` 経由に統一した。あわせて `println(1.0)` のような浮動小数リテラルが `cm_println_int` へ誤ディスパッチされLLVM検証エラーになる問題も修正（全バックエンドで小数出力が一致）
- **WASMのポインタ・文字列スライスのstride不整合を修正**: WASMはポインタが4バイトだがスライスの要素サイズは8バイトのため、`void**` アクセス（4バイト）と sort/reverse/subslice/delete/equal（elem_size=8）でstrideが食い違い、文字列スライスの `sort()` 等が壊れていた。ポインタ要素を8バイトスロットへゼロ拡張して格納するようにし、全処理でstrideを一致させた
- **`return self` が構造体値でなくポインタビットを返す問題を修正（C1）**: メソッドの `self` はポインタだが、`return self` がそのポインタ値を構造体の戻り値スロットへコピーしていたため、native/wasm/jitでビルダーAPI（メソッドチェーン）が全滅していた（jsは偶然正しい）。戻り値がポインタで戻り値型が非ポインタの集約型のときはデリファレンスを挿入して値を返すようにした
- **単相化の型引数kind復元にshort/ushort/tiny/utiny/isize/usizeを追加（M11）**: マングルされた型引数名からTypeKindを復元する2箇所のテーブルがこれらを取りこぼしStruct扱いにしていたため、`Box<short>` の配列フィールドが消える等の実害があった。テーブルを共有ヘルパへ統合し全プリミティブ型を扱うようにした
- **whileループのdeferが毎周期実行されるよう修正（M16）**: `for` はループボディ終了ごとにdeferを実行するのに `while` は関数終了時に1回だけ実行しており非対称だった。`while` にもループボディスコープを設けてdeferを毎周期実行するようにした
- **パーサの固定上限を撤廃（M5）**: 1ブロック1000文・1ファイル10000宣言の固定上限に達すると正当な機械生成コードが「構文エラー」扱いになっていた。進捗（トークン位置が進むか）の検出で無限ループを防ぐ方式に一本化し、宣言数・文数の固定上限を撤廃した
- **整数リテラルの縮小キャストに警告を追加（M4）**: `300 as tiny`（→44）のように範囲外の整数リテラルを縮小キャストしても無警告だったため、切り捨てが起きる場合に警告を出すようにした（実行時の挙動は従来通り）

### 標準ライブラリ: 純粋なCmで書いたJSONパーサ（std::json）

### バグ修正: 名前解決・JSコード生成

- **ローカル変数・引数がimportした引数なし関数と同名のとき、native/jitで不正な結果になる問題を修正**: 例えば `web::html` の `title()` と同名の引数 `title` を `text(title)` に渡すと、HIR loweringがローカルスコープを持たず `func_defs_` の有無だけで関数参照と判定していたため、MIR loweringが `resolve_variable` より前に関数参照へ倒していた。ローカルが解決できる場合は関数参照より優先するよう修正（js/tsはJSのスコープで偶然正しく、native/jitのみ壊れていた）
- **構造体フィールドが構造体配列のとき、JS出力で各要素が `undefined` になり要素代入で落ちる問題を修正**: `Array.from({length: N}, () => {})` はアロー本体の空ブロックと解釈され `undefined` を返していた。要素を括弧で包んで（`() => ({...})`）オブジェクトを返すよう修正。インメモリのアリーナ・ストア構造がjs/tsで正しく動くようになった
- **`string + char` の連結がJSで `cm_char_to_string is not defined` で落ちる問題を修正**: loweringが挿入する組み込み `cm_char_to_string` をJSバックエンドが未対応だった。`String.fromCharCode` へ写像した（JSではcharは数値表現）
- **構造体の配列フィールドへの要素アクセスで配列全体をコピーしていた問題を修正（LLVM最適化スケーリング）**: `struct.arrayField[i]` の読み出しを、MIRが「配列フィールド全体を一時変数へコピー→インデックス」に分解していたため、固定長配列 `[N x T]` の巨大なload/storeが生成され、SROA→InstCombineが配列サイズに対し超線形（実測でO(N²)）に膨張していた（native/jitで大きな配列だとコンパイルが極端に遅くなるか複雑度ガードで中断）。MIR loweringを修正し、メンバアクセスの場所（MirPlace）を土台にIndexプロジェクションを積んで要素だけをコピーするようにした。これによりコンパイル時間が配列サイズに依存しなくなり（arena[16384]でも約0.3s）、生成コードも配列全体コピーが消えて高速化する。`std::json` のアリーナ容量を48→1024へ引き上げられた

### TypeScriptバックエンド（--target=ts）: 型注釈付き出力とフロントエンド連携
