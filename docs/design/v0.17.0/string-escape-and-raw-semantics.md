# R5: 文字列エスケープの黙殺・raw文字列のエスケープ解釈・補間エスケープ不能

**ステータス:** 未修正（構文網羅バグ調査で検出）
**重大度:** High（`\x`/`\u`黙殺）/ Medium（raw非raw・補間エスケープ）

## 症状（実測: cm 0.17.0、プローブ `.tmp/bughunt6/syntax2/`）

### バグ1【High】`\x`/`\u`/`\U`・未知エスケープでバックスラッシュが黙って脱落し誤った文字列を生成

`src/internal/syntax/lexer/lexer.cpp`の`scan_escape_char()`は`\n \t \r \\ \" \' \0`のみ対応。default節が後続文字をそのまま返すため、未知エスケープはバックスラッシュだけ黙って消える。

| 入力 | 期待 | 実出力（jit O0/O2・native O2・wasm・js 全一致） |
|---|---|---|
| `"\x41"` | `A`（len=1） | `x41`（len=3） |
| `"é"` | `é` | `u00e9`（len=5） |
| `"\U0001F600"` | 😀 | `U0001F600`（len=9） |
| `"\q"` | 診断 | `q`（無診断、--strictでもerrors:0） |

`--strict`でも一切診断されない黙殺。パス文字列・バイナリデータ・テスト期待値が静かに壊れる。UTF-8直書き（`"é"`）は`len()`=1/`byte_len()`=2と正しく整合しているため、`\x`系エスケープ経路だけの欠落。

### バグ2【Medium】文字列とcharリテラルでエスケープ挙動が不一致

`"\x41"`は黙って受理される（誤値）が、`'\x41'`（charリテラル）は構文エラー`Expected ';'`（rc=1）。同じエスケープが文字列とcharで黙殺/エラーに分裂。

### バグ3【Medium】raw文字列（バッククォート）がrawでない

Cmのraw文字列は`r"..."`ではなくバッククォート`` `...` ``（`r"..."`/`r#"..."#`は構文エラーで拒否）。しかし`scan_raw_string()`が`\`で`scan_escape_char()`を呼ぶため、`` `C:\path\n` ``の`\n`が実改行になり、未知エスケープ`\p`はバックスラッシュが脱落する。実測: `` `C:\path\n` ``→`C:path`+実改行（len=7、期待は9文字リテラル）。全経路一致。raw文字列の「エスケープ無効」という語義に反する。

### バグ4【Medium】補間のバックスラッシュエスケープが不能

`"\${x}"`はリテラル`${x}`を出すべきところ補間される（→値）。`"$\{x}"`では`$`が黙って消失。通常文字列でリテラル`${x}`を得る自然な手段がなく、裏技`"$$\{x}"`のみ。`\{`は正しくエスケープされるため`$`側の扱いだけ欠落。全経路一致（レキサ段の問題）。

## 修正方針

- `scan_escape_char()`へ`\xHH`/`\uHHHH`/`\UHHHHHHHH`のデコードを実装（UTF-8エンコードして格納）。未知エスケープは診断で拒否（黙って`\`脱落を廃止）。文字列とcharで同一のエスケープ表を共用する（B6のcharリテラル構文エラーも解消）。
- raw文字列（バッククォート）は`\`をエスケープ処理せずリテラルとして格納する（`scan_raw_string`から`scan_escape_char`呼び出しを外す）。補間`${}`のみ特別扱いを維持。
- 補間の`\$`をリテラル`$`のエスケープとして認識する。

## テスト計画

`tests/common/formatting/`（またはstrings）へ: `\x`/`\u`/`\U`の正しいデコードと`len()`/`byte_len()`整合・未知エスケープの診断・raw文字列のバックスラッシュ保持・`\${x}`のリテラル出力を全バックエンド一致で。charリテラルの`'\x41'`受理。
