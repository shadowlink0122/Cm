# Cm大規模開発ボトルネック監査

v0.17.0開発時点のコンパイラ・ランタイム・標準ライブラリを対象に、大規模開発で設計上のボトルネックとなる箇所を7領域（スライス・ジェネリクス・メモリ管理・識別子/名前解決・バックエンド一貫性・コンパイル時間・型システム/言語機能）に分けて調査した結果をまとめる。
全所見は実際に小規模プログラムをjit/native/wasm/js/ts（必要に応じsv）で実行して検証し、根拠となるソース位置（file:line）または再現手順を併記する。
「検証済み」は実行で再現したもの、「疑い」はコード読解に基づく潜在問題を指す。

## 総括: 5つの構造的テーマ

個別バグの多くは、以下の5つの設計上のテーマに帰着する。

1. **黙って壊れる（診断なしの誤コンパイル・文の欠落）**: lowering解決失敗時にエラーを出さずフォールバックする「黙殺パターン」が随所にあり、`self.items.pop()`の欠落・不正キャストの受理・未定義シンボルへの解決（`__error__len`等）として現れる。
2. **バックエンドごとのランタイム重複実装**: native/wasm/js/tsでランタイムが別実装（native 188関数 vs wasm 108関数）であり、シンボル欠落（`cm_free`型のリンク切れ）や挙動分裂（文字列比較・double出力・未初期化値・OOB）が構造的に発生し続ける。
3. **文字列ベースの型同一性**: モノモーフ化の型キーがフラットな`__`連結文字列で非単射のため、ネストした型引数の誤コンパイル・ユーザー識別子との衝突・型置換漏れが発生する。型ディスパッチテーブル（elem_size・push関数選択等）も複数箇所に手書き重複しており同期漏れがstride不一致バグを生む。
4. **メモリを解放しない**: 文字列・スライスの一時オブジェクトは全バックエンドで一切解放されず、RAIIデストラクタはwhile/forループ本体スコープで走らないため、通常のループがリークする。wasmアロケータは解放そのものが不可能。
5. **集約（構造体・配列）を値として動かす経路の未成熟**: 大きな構造体のコピーがmemcpyでなく全要素SSA展開されO2が二次爆発、メソッドから`return self`するとポインタビットが構造体値として返る、インターフェイスを集約に入れると壊れる。

## 領域別の根拠詳細

### スライス/動的配列

`short[]`のstride不一致（C4）は、elem_size計算がfunction.cpp:358-383（ローカル）と487-511（構造体フィールド）に重複し、push関数選択がexpr_slice.cpp:105-131、get選択がaccess.cpp:491-511と、**4箇所の手書きテーブルが独立に保守されている**ことが根因である。
Short/UShortはelem_sizeテーブルにあるのに選択テーブルに無く4バイト関数へフォールバックし、逆にTiny/UTinyはelem_sizeテーブルに無く4バイト確保+1バイトアクセスで「偶然安全」になっている。
構造体フィールド側のelem_sizeテーブルは多次元スライス（Array→32バイト）ケースも欠落している。
`T[] b = a`は全バックエンド一貫して参照セマンティクス（ヘッダ共有）であり関数引数経由の変更も呼び出し元に見えるが、明示的なclone手段が無い。

### ジェネリクス/モノモーフ化

型の同一性がフラット文字列（`base__arg1__arg2`、typeinfo.cpp:89-111）で、`__`は正当な識別子文字のため`Box__Box__int`は`Box<Box<int>>`とも`Box<Box,int>`とも区別できない。
置換処理（mono_internal.cpp・mono_structs.cpp:126-143）はこの名前を`__`/`<>`/`,`で再分解しており、ネスト型引数（C7）・ユーザー識別子衝突（C8）・`type_args.clear()`の場当たり的散在の根因になっている。
`Node<K,V>[N]`フィールドは以前のLLVMハードエラーから**無診断の誤値**に変化しており、むしろ悪化している。
不動点ループ（driver.cpp:61-104）はMAX_PASSES=64超過時に無診断で脱出し、テンプレート削除後に未特殊化呼び出しが残る。

### メモリ管理

設計意図は手動管理+RAII（docs/archive/legacy/spec/memory.md）だが、コンパイラ都合の一時オブジェクト（concat・format・map/filter/sort結果等）を解放するdropパスが存在しない。
`emit_scope_destructors`の呼び出し元は明示ブロック（stmt/control.cpp:407）と関数終了のみで、`lower_while`はスコープ管理なし、`lower_for`はdeferのみ実行しデストラクタを呼ばない。
実測: ループ内`Vector`はN=8Mで124MB（線形リーク）、同じ本体を`{}`で囲むとNに依らず1.3MBで平坦。
文字列連結ループはN=200kで4.6秒（二次時間）、interpreterではN=100kでRSS 1GB。

### 識別子/名前解決

「生成コードの変数重複」の報告に対し、tests/common配下411本のJS生成物を`node --check`で機械検査した結果、ローカル変数・一時変数の再宣言は0件だった（`名前_localId`サフィックスで一意化、emit_function.cpp:406-407）。
実際に起きるのは関数定義レベルの衝突であり、メソッドマングリング（expr_member.cpp:987で`Struct__method`）が自由関数・モジュール修飾名（`A::b`→`A__b`）と同一キー空間を共有し、衝突時にガード無く片方が消える（C16）。
過去のimport関数シャドーイング修正（basic.cpp:362）の兄弟形（代入LHS・メソッドベース・引数渡し）は全て正しく動作することを確認した。
JS/TSの予約語は`_cm_`プレフィックスで退避され健全、SVは予約語をハードエラーにするが構造体フィールド名とマングリング済みメソッド名は未検査。

### バックエンド一貫性

operators.cppのEq/Neにはポインタ→`cm_strcmp`分岐があるがLt/Le/Gt/Ge（481-501）には無く、文字列比較がアドレス比較に落ちる（C2）。
wasmのcm_println_double/float（wasm/runtime_print.c:142-160）は`(int)value`で切り捨てるスタブのまま。
ランタイム定義数はnative 188 vs wasm 108で、コード生成が参照しうる`cm_double_to_string`・`cm_uint_to_string`はwasm TUに無い（現在は偶然未参照の潜在リンク切れ）。
ゼロ除算・オーバーフロー・通常域キャスト・char演算・slice/string主要メソッド・TreeMap・std::jsonは全バックエンド一致を確認した。

### コンパイル時間

構造体コピーは`load %S`/`store %S`の第一級集約として出るため（`CreateMemCpy`使用ゼロ）、O2のSROA/instcombineが要素数に対し超線形に膨張する（C14）。
コード生成は単一の`std::thread`（safe_codegen.hpp:63）で実行され、CPU使用率は0.79コアを超えない。
インクリメンタルビルドは削除済みで、ドライバは常に`compileWithModuleInfo(mir, {})`（backend/llvm.cpp:171）の空キャッシュ全体コンパイルを行う。
モノモーフ化自体は線形（200インスタンスで0.3秒）、菱形importは一度だけ処理、循環importは0.07秒で即エラーと健全。

### 型システム/構造体

`return self`のMIRは`_4 = copy(_1)`（*C）→`_0 = copy(_4)`（C）とデリファレンス無しにポインタを戻り値スロットへコピーしている（C1）。
派生Ordのlowering（auto_impl_compare.cpp:330-335,381-387）はStructフィールドのみ`__op_lt`へ再帰し、Stringは素の`MirBinaryOp::Lt`になる（ユーザーコードの文字列`<`はstrcmp化されるのに派生本体には届かない）。
値セマンティクスの中核（代入コピー・値渡し隔離・3段ネストコピー・混在フィールドレイアウト・構造体配列stride・union payload・match網羅性）は全バックエンドで正しいことを確認した。

## 健全と確認された点（調査範囲の境界）

- ローカル変数・一時変数のJS/TS出力は411本機械検査で重複ゼロ、ラムダ・match armのスコープ分離も正しい。
- スカラ・構造体の値セマンティクス、混在フィールドのレイアウト/アライメント、union、match網羅性チェック、通常域の数値キャストは全バックエンド一致。
- `<T: Ord>`制約宣言時の違反検出、循環import即時エラー、菱形importの単一処理、モノモーフ化の線形スケール、`fmt`の冪等性。
- 過去に修正したバグ（メンバスライスpush・import関数シャドーイング・インクリメント黙殺）の兄弟形の多くは再検証で健全（ただしpop/delete/clearの兄弟は残存=C11）。

## 推奨対応ロードマップ

### 第1段: 局所修正で被害が大きいもの（各1箇所〜数箇所の修正）

1. 文字列比較演算子のLt/Le/Gt/Geへ`cm_strcmp`分岐追加（operators.cpp、C2）。
2. 派生Ordの文字列フィールドを内容比較へ（auto_impl_compare.cpp、C3）。
3. `return self`のデリファレンス挿入（C1）。
4. wasm `println(double/float)`を`cm_format_double`経路へ（C15）。
5. `as string`等の不正キャストを型検査で拒否（C10）。
6. メンバスライスpop/delete/clearへ`get_member_place`適用+解決失敗時ハードエラー（C11）。
7. short/ushort用スライスランタイム追加またはelem_size駆動の統一パスへ（C4）。
8. `sort()`のelem_size別ディスパッチまたは非対応型の型検査拒否（C5）。

### 第2段: 構造的テーマへの対処

1. **黙殺禁止インバリアント**: lowering中の場所解決失敗は必ず診断付きハードエラーにする（expr_slice.cpp:70,163,224,258,290等の全フォールバックを洗い出し）。
2. **型ディスパッチの一元化**: elem_size計算とランタイム関数選択を網羅的switchの共有ヘルパ1箇所に統合し、ケース漏れをコンパイルエラー化。
3. **型同一性の構造化**: フラット`__`文字列を再帰的な型キー（または可逆エンコーディング）へ置換し、C7/C8/C9とtype_args.clear()の散在を一掃。
4. **dropパス導入**: コンパイラ一時オブジェクトのlast-use解放と、while/forループ本体でのスコープデストラクタ/defer実行（C12/C13/M16）。
5. **集約コピーのmemcpy化とbyval/sret渡し**: サイズ閾値超の構造体を第一級SSA値にしない（C14/M12）。
6. **マングリング衝突検出**: 全マングル名を単一シンボルテーブルに登録し衝突をハードエラー化（C16/M2）。

### 第3段: スケール基盤

1. インクリメンタルビルド復活（既存の`compileModules`キャッシュ経路の接続）とモジュール並列コード生成（H14）。

3. 可視性（export）の強制（H7）、`Option<V>`返しのマップAPI（H8）、StringBuilder導入（H9）。
4. definite assignment/return網羅解析（H6）と境界チェックの統一ポリシー（M1）。
5. パーサ固定上限の撤廃（M5）、タイムアウトのプロセス分離（M6）、ランタイムの共通コア化（native/wasm/jsの挙動仕様を単一実装+薄いプラットフォーム層へ）。
