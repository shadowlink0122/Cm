# モジュールグラフのテキスト手術脱却（包含判定と出力のAST化）

## 概要

module-system-structural-imports（archive済み）でimportのテキストインライン展開は廃止されたが、実測ではAST駆動なのは宣言・辺（import/export）の認識までで、選択的包含の判定と出力組み立てはテキスト手術のまま残っている（module/graph.cpp、約1000行）。

- **包含判定**: 関数本文のスパンをソース文字列から切り出し、正規表現`[A-Za-z_][A-Za-z0-9_]*`で識別子を収集（collect_identifiers/strip_for_scan、graph.cpp:73-143・:578-597）して「名前が出現したら包含」で決めている。
- **出力組み立て**: blank_linesによるスパン消し込み（:212、宣言・import行の空行化）、関数スパンのerase、エイリアスimportの改名テキスト複製（rename_copies :790/:818）、module形importのnamespaceテキスト包み（:827以降）というスパン演算の積み重ねで最終ソースを合成している。

## 弊害

- 識別子の字面一致で包含が決まるため、ローカル変数や別モジュールの同名シンボルで過剰包含が起き、コメント/文字列の除去はstrip_for_scanの手書き字句処理に依存する（補間断片の扱い等、字句仕様が変わるたびに追従漏れの危険がある）。
- スパン演算はソース座標に強く依存し、X5（構文エラー位置がimport展開後座標になる）と同根の座標ズレ問題を構造的に抱える。
- 改名複製・namespace包みがテキストで行われるため、複製されたコード内の補間・ネスト構文に対する変換の正しさをパーサを通すまで保証できない。

## リファクタリング方針

1. **第1段（判定のAST化）**: 各関数の参照シンボル集合を、パース済みASTのwalk（識別子ノード・呼び出し名・型名の収集）で構築し、regexスキャン（collect_identifiers/strip_for_scan）を削除する。包含クロージャの計算（include_function）は集合の中身が正確になるだけで機構は不変のため低リスク。
2. **第2段（出力のAST化）**: 包含した宣言のASTを直接次段へ渡す（または宣言単位のプリティプリントで再構成する）ことで、blank_lines・スパンerase・改名テキスト複製・namespaceテキスト包みを廃止する。エイリアス改名はASTのシンボル改名として行う。
3. 座標情報は宣言ノードの元ファイル・元行を保持し、診断が常に元ソース座標で出るようにする（X5系の恒久解消）。

## リスク

- 出力のAST化はプリティプリント経由になるため、フォーマッタ（fmt/formatter.cpp）との整合と、コメント保存の要否を仕様決定する必要がある（包含出力は中間生成物でありコメント破棄が妥当か）。
- 段階を分けることで、判定AST化（第1段）だけでも過剰包含・誤除外バグ族を先に封じられる。

## テスト計画

- 同名シンボル（ローカル変数と関数・2モジュールの同名関数）・文字列/コメント内の偽出現・補間内参照の包含判定回帰。
- エイリアスimport・階層再export・module形importの既存スイート全数。

## 検出経緯

全体複雑度レビュー（2026-08-05）でmodule/graph.cppを実査し、構造化import移行の到達範囲を確認した。
## 実装記録（テスト計画の実施と発見バグの修正・2026-08-08）

第1段（判定のAST化）に先立ちテスト計画の包含判定回帰を実装したところ、graph本体は健全で、**実害は補間プレースホルダの受理リスト側**にあることが判明した。

- **graph本体の検証結果（健全）**: 補間プレースホルダ内でのみ参照される関数の包含（strip_for_scanは文字列を除去するが補間内部`{...}`は保持する設計が機能）・コメント/文字列内の偽出現の無害性・プライベート改名（__cm_priv_*）の定義/参照の整合を実プローブで確認した。
- **発見した実害（修正済み）**: importの非exportヘルパーを補間内でのみ呼ぶと、プライベート改名後の`__cm_priv_*`名がMIRの補間プレースホルダ受理ホワイトリスト（R20で!~-を追加した箇所）に**先頭'_'が無い**ため文字列全体が未変換で素通りし、`value={__cm_priv_util2_0_hidden_helper()}`がそのまま出力されていた（checker側の脱糖は制限なしで乖離・全バックエンド共通）。受理リスト2箇所へ'_'を追加し、&/*形式の内側識別子も'_'許可した。さらに通常文字列リテラルの検出側リスト（expr/basic.cpp）は'_'に加えR20の!~-(も未追従で、戻り値文字列内の`{-a}`等が素通りしていた——検出側を抽出側と同一の受理文字へ揃えた。
- 回帰: modules/interp_private_helper.cm（改名ヘルパーの補間経由解決）・strings/interpolation/underscore_placeholder.cm（先頭_識別子と戻り値文字列内R20演算子）。全13スイートPASS。

**残り（本提案の本体）**: 第1段（包含判定のAST化＝regexスキャン置換。識別子ウォーカの網羅実装が必要で、走査漏れは未包含のコンパイルエラーとして顕在化する）・第2段（出力のAST化）。教訓: 受理/検出のホワイトリストが2系統3複製あり文字追加のたびに追従漏れする——第1段実施時に単一の述語へ統一すべき。
## 実装記録（第1段・判定のAST化・2026-08-08）

第1段（包含判定のAST化）を実施した。

- 参照識別子の収集を、正規表現テキストスキャン（collect_identifiers+strip_for_scan）からパース済みASTのwalk（AstRefCollector）へ置き換えた。収集方針は従来と同じ「出現した識別子は全て包含候補」（過剰包含は無害・過少包含はリンク欠落で即顕在化）で、修飾名A::Bはセグメント分割、文字列リテラルは補間プレースホルダ内部のみを識別子走査する（strip_for_scanの文字列規則と同一）。関数はFunctionDecl（export宣言付き含む）を自関数のrefsへ、それ以外の宣言（struct/global/typedef/enum/interface/impl/macro・rootのmodule内部）はrest_refsへ収集し、Import/Export(List系)/非rootモジュール/FFI宣言名の除外規則も従来と一致させた（FFI宣言はシグネチャ型のみ収集）。
- 包含クロージャの計算（include_function）は不変。CM_GRAPH_TEXT_SCAN=1で従来のテキストスキャンへフォールバックできる切り分け経路を残した。
- 検証: 全13スイート一発PASS（600超のプログラム・libs全30モジュールのimportゲート・選択import/エイリアス/階層再export/namespace含む）で判定の同値性を実証した。ウォーカの走査漏れは未包含のコンパイルエラーとして即顕在化する性質を検証設計に用いた。
- これによりstrip_for_scanの手書き字句処理（補間断片・エスケープの追従）への依存が包含判定から消え、字句仕様変更時の追従漏れバグ族を封じた。

残り: 第2段（出力のAST化＝blank_lines・スパンerase・改名テキスト複製・namespaceテキスト包みの廃止とプリティプリント出力・元ソース座標の恒久保持）。テキストスキャン実装はフォールバックとして残置しており、第2段完了時に削除する。

## 実装記録（第2段＝テキスト変換の精密化とプリティプリント案の却下・2026-08-11）

第2段の目的「出力組み立ての変換の正しさをパーサを通す前に保証できない問題の解消」を、出力の完全AST化（プリティプリント）ではなくテキスト変換の精密化で達成し、文書を完了とする。

- **実害の発見と修正（改名のトークン精密化）**: 従来の`\b`正規表現によるプライベート改名・エイリアス改名複製は、文字列リテラルの内容・コメント内の同名語も書き換えていた（実測: 改名対象ヘルパー名を含む文字列`"call hidden_calc for doubling"`の内容が`__cm_priv_*`へ改名される無言の内容破壊）。`rename_identifiers`を新設し、strip_for_scanと同じ走査規則（コメントは対象外・通常文字列は補間プレースホルダ`{...}`内部のみ対象・raw文字列（バッククォート・複数行可）は`${...}`内部のみ対象・charリテラルは丸ごと通過）で識別子トークンのみを改名するよう2箇所（priv_renames・rename_copies）を置き換えた。raw文字列はstrip_for_scan（フォールバックの走査側）も従来未対応で、内容中の`"`が文字列状態を反転させ後続コードの走査を壊しうる盲点だったため同時に対応した。回帰は`tests/common/modules/priv_string/`（通常文字列・raw文字列の内容保存＝`"`と複数行含む・`{...}`/`${...}`補間内改名の解決）で固定。
- **プリティプリント案の却下（設計判断）**: 出力の完全AST化は、(1)正確な原文テキストを再生成テキストへ置き換えるため忠実性がむしろ低下する（コメント・書式の喪失、プリンタ自体のバグ面）、(2)全構文を網羅するAST→Cmソースプリンタという大型新規部品を要する（fmt層はテキスト整形でAST非対応）、(3)残るテキスト操作の内訳が精密化後は安全——blank_lines・関数スパンeraseは宣言全体の内容非依存な消去・namespace包みはラッパ行の付加のみで内容変換を含まない——ため、費用対効果が成立しない。原文スパン出力＋トークン精密変換を本設計の最終形とする。
- **座標（X5系）**: モジュール別範囲（module_ranges）とSourceLocationManagerの接続（構文エラー診断の位置情報付き表示）は別文書の処置で対応済みであり、第2段の残項目ではない。
- これにより本文書の全段階（第1段=判定のAST化・第2段=出力変換の精密化）の処置が完了した。テキストスキャンのフォールバック（CM_GRAPH_TEXT_SCAN=1）は判定側の切り分け用として存置する。
