# R24: 文字列補間が実行時値に含まれる波括弧で破壊される（Debug出力等）

**ステータス:** 修正済み（評価済み値の波括弧をエスケープ挿入し「評価結果は再スキャンしない」不変条件を確立）
**重大度:** Medium

補間プレースホルダの式が返す**実行時の文字列値**が`{`/`}`を含むと、その値と後続のプレースホルダの出力が破壊される。Debug出力（`P { x: 1, y: 2 }`のように常に波括弧を含む）を補間に埋めると直撃する。既修正のL2（補間のネスト誤パース）はプレースホルダ内の**リテラル**波括弧を扱ったが、これは**メソッド戻り値に実行時に現れる**波括弧という別経路。

## 症状（実測: cm 0.17.0、プローブ `.tmp/bughunt8/{derive,verify}/`）

```cm
struct P with Debug, Display { int x; int y; }
int main() {
    P a = { x: 1, y: 2 };
    println("dbg={a.debug()} disp={a.toString()}");
    return 0;
}
```
実測（現行バイナリ）: `dbg=P (1, 2) disp={}`
期待: `dbg=P { x: 1, y: 2 } disp=(1, 2)`

`a.debug()`は`P { x: 1, y: 2 }`（波括弧を含む）を返すが、その波括弧を補間エンジンがプレースホルダ区切りとして再解釈し、以降の対応が総崩れになる。`dbg=`には`a.toString()`の値`(1, 2)`が漏れ込み、`disp=`には空`{}`が出る。derive生成物自体は正しい（別printで`debug()`単独出力は正常）ため、原因は補間エンジンが**プレースホルダの評価結果に含まれる波括弧を再スキャンしてしまう**点にある。`with`形式でも再現。

## 論点と方針

補間の脱糖（type-resolution-simplificationで導入したパース時脱糖`desugar_interpolation_parts`）は、ソース文字列の波括弧をプレースホルダ境界として正しく分割する。問題はその先で、プレースホルダ式を評価した**戻り値の文字列**を最終出力へ連結する際に、戻り値の中身を再度補間解釈している（またはフォーマット関数が値中の波括弧をエスケープ対象として扱っている）ことにある。修正は、プレースホルダの評価結果は不透明な文字列として扱い、二度と補間解釈しないこと（値の波括弧はリテラルとして素通しする）。R20（単項~の補間破壊・書式のバックエンド分岐）と同じ補間/フォーマット経路の別症状で、まとめて補間エンジンの「評価済み値は再スキャンしない」不変条件を確立するのが筋。

## テスト計画

`tests/common/formatting/`へ: 波括弧を含む文字列を返す式（`debug()`・`"{literal}"`を返す関数・波括弧入りstring変数）を補間に埋め、後続プレースホルダと混在させた出力が全バックエンドで正しいことの回帰。Debug/Display derive出力の補間埋め込みを固定。

## 実装記録

- 真因はランタイムの置換連鎖の構造欠陥: `cm_format_replace_int(format, v1)`→`cm_format_replace_string(結果, v2)`…の各呼び出しが文字列先頭からプレースホルダを再走査するため、直前に挿入した評価済み値の`{`/`}`を次の呼び出しがプレースホルダ区切りとして再解釈していた。
- **native/jit**: `cm_format_replace`（全replace_*が使う共通スプライス）で挿入値中の波括弧を`{{`/`}}`へエスケープして挿入するようにした。後続走査の`cm_find_placeholder_start`は`{{`をスキップし、チェーン最終段の`cm_format_unescape_braces`（既存）がリテラルへ復元する——「評価済み値は再スキャンしない」不変条件が置換の物理表現として成立する。
- **wasm**: 複製ランタイムの`cm_format_replace`へ同一エスケープを実装し、replace_int/replace_stringが持っていた独自スプライスを共通`cm_format_replace`呼びへ集約した（エスケープの一元化と複製削減）。
- **js/ts**: `__cm_format_string`は単一パスのString.replaceで挿入値を再走査しないため元々健全（無修正）。
- 回帰: Debug/Display derive出力（`P { x: 1, y: 2 }`）と波括弧入り文字列を返す関数を後続プレースホルダと混在させ、jit/native/wasm/jsの4経路一致を確認。
