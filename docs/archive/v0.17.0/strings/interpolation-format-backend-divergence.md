# R20: 文字列補間・書式指定子のバックエンド分岐（単項~の補間破壊・幅/科学記法の不一致）

**ステータス:** 修正済み（単項演算子の受理・js安全側統一・数値書式の全バックエンド一元化。正準仕様はC/printf互換）
**重大度:** Medium

TSバックエンド調査中に発見した、native/jitとjs/tsで文字列補間・書式指定子の結果が食い違う2件。TS固有ではなくバックエンド間の意味分裂（これまでの調査で補間はV/W/L2で徹底調査したが、単項演算子と書式指定子のこの経路は未検出だった）。

## 症状（実測: cm 0.17.0、プローブ `.tmp/bughunt7/{ts,verify}/`）

### バグ1【Medium】単項`~`を含む補間が全プレースホルダを破壊し、バックエンドで症状が異なる

```cm
int main() { int a = 240; int n = 5; int r = 9; println("bad={~a} good={n} also={r}"); return 0; }
```
実測:
- js / ts: `bad=undefined good=undefined also=undefined`（**隣接する正当な`{n}`/`{r}`まで巻き込んで全滅**）
- jit / native: `bad={~a} good={n} also={r}`（文字列全体を非補間として素通し）

補間パーサが単項`~`をプレースホルダ式として扱えないのが前段の原因。そこから先が分裂し、js/tsは値配列が空のまま全`{...}`を`values[idx++]`=undefinedで置換してデータ破壊、jit/nativeは文字列全体をリテラル扱いする。どちらも計算値を出さないが、js/tsは無言でデータ破壊する点が危険。二項演算子の補間（`{a & b}`・`{a << b}`）は3経路健全。

### バグ2【Medium】書式指定子の幅・科学記法がnative/jitとjs/tsで不一致

```cm
int main() { int n = 255; double pi = 3.14159265; println("pad={n:6} sci={pi:.2e}"); return 0; }
```
実測:
- js / ts: `pad=   255 sci=3.14e+0`（幅6の右詰め・科学記法を適用）
- jit / native: `pad=255 sci=3.14`（幅指定を無視・科学記法の指数を落とす）

幅・左寄せ（`:6`/`:<6`）と科学記法（`.2e`）でnative/jitが指定を無視する。ゼロ埋め（`:06`→`000255`）は3経路一致。js/ts側が仕様に沿う出力で、native/jit側の書式適用欠落の疑いが強い。

## 修正方針

- **バグ1**: 補間パーサでプレースホルダ式に単項演算子（`~`・`!`・単項`-`）を受理させる（二項は既に健全なので、単項プレフィックスの取りこぼし）。あわせて、パース不能なプレースホルダに遭遇したときjs/tsが「値配列が空でも`{...}`を消費してundefined置換する」挙動を、native/jit同様の安全側（リテラル保持）か明示エラーへ統一し、無言のデータ破壊を止める。
- **バグ2**: 幅・左寄せ・科学記法の書式適用をnative/jitランタイムの`__cm_format_string`相当へ実装し、js/tsと出力を揃える（書式指定子の意味論を全バックエンドで単一仕様に）。どちらを正とするかはCANONICAL_SPECの書式仕様で確定する。

## テスト計画

`tests/common/formatting/`へ: 単項演算子を含む補間（`{~a}`・`{-a}`・`{!b}`）・隣接プレースホルダとの混在・書式指定子（幅/左寄せ/科学記法/ゼロ埋め）の出力が全バックエンド（jit/native/wasm/js/ts）で一致することのマトリクス回帰。

## 実装記録

- **バグ1（単項演算子の補間破壊）**: MIRの`extract_named_placeholders`のプレースホルダ先頭文字ホワイトリストに`~`と単項`-`が欠けていた（`!`はあった）。許可を追加し、`{~a}`/`{-a}`/`{!b}`が全バックエンドで正しく補間される。あわせてjs/tsランタイムの`__cm_format_string`を「値が尽きたプレースホルダはリテラル保持」へ変更し、パース不能な内容の位置ずれで隣接プレースホルダまでundefined置換するデータ破壊をやめた（native/jitの素通しと安全側で一致）。
- **バグ2（書式指定子の分裂）**: 正準仕様を**C/printf互換**（`{pi:.2e}`→`3.14e+00`・指数2桁ゼロ埋め・`:e`の既定精度6桁・数値の幅は右詰め既定・`:06`ゼロ埋めは符号を先頭保持）に確定し、3実装を揃えた——(1)native/jitランタイム（runtime_format.c）へ`cm_apply_numeric_spec`（幅・整列・フィル・ゼロ埋めの一元適用）と`cm_format_double_exp_prec`（精度つき指数）を実装し、replace_int/uint/long/ulong/doubleを型文字ディスパッチ+spec適用へ再編（`:8x`等の幅+基数複合も対応）。(2)wasmランタイム（複製）へ同一のヘルパを移植し、既存のalign解析があるのに既定整列が無く幅が無視されていた穴も修正。(3)jsランタイムの`__cm_format`へ指数2桁化（`__exp2`）・`:e`既定精度6・幅+基数複合の一般化マッチャ・ゼロ埋め符号保持を実装。
- **バックエンド別expectの解消**: 分裂を吸収していた`tests/common/formatting/basic_format.expect.js`を削除（4バックエンド同一出力になったため）。
- **回帰**: `format_spec_matrix.cm`（幅/左寄せ/中央/ゼロ埋め/long幅/16進幅/フィル文字/負数ゼロ埋め/科学記法/精度をjit/native/wasm/jsで一致検証）・`interp_unary_ops.cm`（単項~/-/!と隣接プレースホルダ）。
- **残課題**: 補間で挿入した実行時値の波括弧再スキャン（R24）は別件。文字列値への幅適用は現状対象外（数値のみ。仕様化は将来）。
