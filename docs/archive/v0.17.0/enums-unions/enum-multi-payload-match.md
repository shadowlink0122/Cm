# enum複数ペイロードのmatch束縛不能とアリティ検査欠落

## 概要

複数ペイロード付きenumバリアント（`Rect(int, int)`）は宣言・構築が受理されるのに、matchパターンで複数値を束縛する構文（`Shape::Rect(w, h)`）が構文エラーになり、格納した値を取り出す手段がない。
さらにペイロード個数に満たないパターン（`E::R(a)`で2値バリアントの1値のみ束縛）が診断なしで受理され、先頭ペイロードだけが束縛される。
機能の入口（宣言・構築）と出口（分解）の実装が非対称で、書けるのに読めないデータを作れてしまう。

## 再現コード

```cm
import std::io::println;

enum E {
    R(int, int),
}

int main() {
    E e = E::R(3, 4);          // 宣言・構築は受理される
    match (e) {
        E::R(a, b) => println("{a} {b}"),  // 構文エラー: Expected ')'（カンマで解析が壊れる）
    }
    match (e) {
        E::R(a) => println("{a}"),         // 受理されて 3 を出力（アリティ不一致が黙認される）
    }
    return 0;
}
```

## 現象

| 操作 | 結果 |
|---|---|
| `enum E { R(int, int) }`宣言 | 受理 |
| `E::R(3, 4)`構築 | 受理（値は格納される） |
| `E::R(a, b)`パターン | 構文エラー（`Expected ')'`） |
| `E::R(a)`パターン（アリティ1 < 2） | 診断なしで受理、aに先頭値3が束縛 |

## 根因候補

matchパターンのパーサがバリアントパターンの括弧内を単一束縛識別子のみ受理し、カンマ区切りの複数束縛に対応していない。
型検査もパターンの束縛数とバリアント宣言のペイロード数を照合しておらず、不足束縛が素通りする。
構築側（enum値のlowering）は複数ペイロードをタプル的に格納できているため、パターン側だけが未実装とみられる。

## 修正方針

パターンパーサの`Variant(識別子)`を`Variant(識別子, 識別子, ...)`のカンマ区切りへ拡張し、各束縛をペイロード位置に対応させてloweringする（束縛スロットは既存の単一束縛の複数化で、MIR側はペイロードごとのフィールド抽出）。
型検査にパターン束縛数とバリアント宣言ペイロード数の一致検査を追加し、不一致は位置情報付きのコンパイルエラーにする（`_`によるワイルドカード束縛を許すかは既存パターン仕様に合わせて決定する）。
全バックエンド（native/jit/js/wasm/interp/sv）のmatch loweringが共通MIR経由であることを確認し、経路差があればそれぞれ追従する。

## テスト計画

- 2値・3値ペイロードのmatch束縛（値の順序検証込み）を全バックエンドで検証する
- アリティ不一致（不足・過剰）がコンパイルエラーになることをerrorsカテゴリで固定する
- ネストmatch（`Option<E>`のSome腕内で`E::R(a, b)`）とガード条件併用も追加する

## 解決記録（実装済み: 設計準拠の宣言エラー化）

調査の結果、enumペイロードは設計上単一値のみ（decl.hpp EnumMemberの設計コメント「1つのフィールドのみ許可。複数値が必要な場合は構造体で包む」）であり、複数ペイロード対応はmatchパターンの未実装ではなく「宣言を黙って受理してデータを落とす」側のバグと判断した。
修正: 型検査（decl.cpp）で複数ペイロードのバリアント宣言を診断付きコンパイルエラーにし、構造体で包む回避策をメッセージで案内する（`Rect(RectData)`形式は従来どおり動作し、matchで`Rect(d)`→`d.w`/`d.h`で全値へアクセスできる）。
これによりアリティ不足パターンの黙認も宣言段階で構造的に発生しなくなった。
回帰テスト tests/common/errors/enum_multi_payload_error.cm（エラー発火）と既存の単一/構造体ペイロードの動作維持を確認した。
