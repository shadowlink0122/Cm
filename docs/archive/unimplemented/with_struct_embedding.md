# 提案: `with` 構文による構造体メンバの引き継ぎ（埋め込み）— 見送り

提案日: 2026-07-11判断: **見送り（不採用）** 2026-07-11関連: [v0.16.0 設計10 `#[derive]` 属性](../../design/v0.16.0/10_derive_attribute.html)

## 提案内容（原案）

自動実装の責務を `#[derive]`（設計10）へ移した後の `with` を、構造体メンバの引き継ぎ（埋め込み継承）に転用する案だった。

```cm
struct A {
    int x;
    int y;
}

struct B with A {
    int z;
}
// B は x, y, z を持つ（提案時の想定）
```

検討していたセマンティクス: フラット化埋め込み（A のメンバを B のレイアウト prefix に配置）、名前衝突・循環・default 重複はエラー、コンストラクタ/デストラクタは引き継がない、複数基底は宣言順に展開。

## 見送りの理由

1. **継承のメリットが限定的**: 実装継承（メンバ・メソッドの暗黙引き継ぎ）が言語にもたらす利点は限られており、Rust・Go などのモダン言語は意図的にクラス継承を採用せず、composition（合成）+ interface/trait で代替している。Cm も interface・`#[derive]`・ジェネリクスで同じ設計空間を既にカバーしている。
2. **破壊的変更の回避**: この転用は「`with <interface名>` の非推奨化→エラー化」を前提としており、v0.9.0 からリリース済みの構文を壊す。設計10 は `with` を残したまま `#[derive]` を追加する方針（非破壊）に改訂されたため、転用の前提自体が消えた。
3. **複雑さがロードマップと競合**: interface 引き継ぎまで踏み込むと、self の型不一致・多重埋め込みのダイヤモンド問題・fat struct 動的ディスパッチとの整合・MIR パス順序（自動実装生成 Pass 1.5 / モノモーフィゼーション Pass 5）への影響など、コンパイラ複雑度が大きく上がる。v0.17.0「バックエンド意味論の完全一致」・v0.18.0「仕様凍結」を控えた時期に導入するリスクが高い。
4. **明示性の設計方針とのズレ**: CANONICAL_SPEC は型推論でも明示的宣言を原則としており、暗黙にメンバ・impl が増える埋め込みはこの方針と整合しにくい。

## 代替手段（現行機能で可能な書き方）

メンバ再利用は明示的な合成で書ける:

```cm
struct A {
    int x;
    int y;
}

// 合成: A をメンバとして持つ（アクセスは b.base.x）
struct B {
    A base;
    int z;
}
```

- 比較・表示などの導出は `#[derive(...)]` / `with` を各 struct に明示的に指定する（導出は構造的合成なので、メンバに struct を含む場合も再帰的に機能する）。
- 共通の振る舞いは interface + `impl <型> for <interface>` で共有する。
- 型をまたぐ共通処理はジェネリクス + インターフェース境界（`<T: Eq + Ord>`）で書く。

## 検討記録: interface 引き継ぎのトレードオフ分析

将来この提案を再評価する場合に備え、埋め込みを導入した場合の「A に使える interface を B でも使えるようにする」3案の分析を残す。

### 案1: 引き継がない（メンバのみ）

- B で必要なら `#[derive(...)]` を再指定するか `impl B for I` を書く。
- 実装コスト小・意味論の追加なし。derive は構造的合成なので展開後の B の全メンバに対して正しく再合成される。
- 欠点: 手書き `impl A for I` は再利用できず、B 用の委譲を手書きする必要がある。

### 案2: derive 由来 interface の自動引き継ぎ

- 埋め込み展開時に基底の `auto_impls` を union するだけで実装コストは小〜中。
- 論点: 暗黙に impl が増える（明示性方針とのズレ）、B が導出不能なメンバを追加すると「A 由来の derive」が遠隔エラーになる（発生源明示診断が必須）、opt-out 構文が必要。

### 案3: 手書き impl を含む完全引き継ぎ（委譲/継承）

- 委譲 impl の自動生成、または prefix 保証を利用した `B*` → `A*` 暗黙アップキャストで実現する案。
- 問題点: self の型不一致（実装本体は A として型付け）、override を許すと仮想ディスパッチ相当が必要、多重埋め込みのダイヤモンド/メソッド衝突、interface 値（fat struct + 関数ポインタ）の vtable 整合、コンパイラ複雑度の増大。実装コスト大。

### 比較表

| 観点 | 案1: メンバのみ | 案2: derive 自動引き継ぎ | 案3: 完全引き継ぎ |
|---|---|---|---|
| 実装コスト | 小 | 小〜中 | 大 |
| 追加される意味論 | なし | 暗黙の derive 伝播 | メソッド解決規則・衝突規則・アップキャスト |
| 診断の難しさ | 低 | 中（発生源の明示が必須） | 高（ダイヤモンド・override） |
| 明示性（Cmの設計方針との整合） | ◎ | △ | △ |
| 類似言語 | Rust（継承なし・derive 明示） | Go embedding の派生形 | C++ 単一継承 / Go のメソッド昇格 |

## 再評価の条件

- 明示的な合成（`A base;` メンバ）+ 再 derive の記述が実用上のボトルネックになっている具体的な事例が蓄積した場合。
- 再評価する場合も、暗黙継承ではなく明示委譲構文（案3の変形）を優先して検討する。
