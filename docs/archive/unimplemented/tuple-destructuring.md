# タプル型・分解代入（見送りの検討記録）

**ステータス:** 未実装（設計判断として見送り。v0.17.0で専用診断を整備）

## 検討の経緯

括弧付き型の宣言（`(int) k = 5;`。局所処理調査A1）の導入時に、`(a, b) = 7;` や `(a, b) = 7, 1;` のようなカンマ区切り括弧形の扱いを検討した。現状はいずれも構文エラーであり、v0.17.0で専用診断「タプル型・分解代入は未対応です（値のグループ化には構造体を使用してください）」へ整備した（型位置 `(int, string)` と式位置 `(a, b)` の両方）。

## 見送りの理由

1. **タプル型が存在しない**: 分解代入の本命ユースケースは多値戻り値（`(a, b) = f();`）だが、Cmの関数はタプルを返せない。並列代入 `(a, b) = 7, 1;` とswap `(a, b) = b, a;` だけでは構文追加のコストに見合わない。
2. **カンマの文法衝突**: 右辺 `7, 1` にはカンマ式またはタプルリテラルの文法が必要で、関数引数・配列リテラル等の区切りカンマと衝突する（`f((a, b))` はタプル1引数か2引数かが曖昧になる）。
3. **設計原則**: 文単位の特例構文の追加は「局所処理」（正準文法からの複製・ドリフト）の温床であり、導入するならタプル型・多値戻り値・分解宣言（`let (a, b) = ...`）を含む一貫した設計文書からの5ステップで行うべき。

## 将来導入する場合の前提

- タプル型 `(T1, T2)` の型システム導入（型検査・レイアウト・全バックエンドのlowering）
- 関数の多値戻り値と呼び出し規約（sret相当の展開）
- 分解代入・分解宣言の左辺値検査（swap時の評価順序保証を含む）
- 既存の括弧型 `(int)`・括弧式 `(a + b)`・ラムダ `(a, b) => ...` との文法整合

現状の代替は構造体（`struct Pair { int a; int b; }`）による値のグループ化。
