# v0.16.0 実装設計 7: ツーリングUX — #構文ハイライトと条件ブロックのインデント

優先度: 追加（ユーザー要望 2026-07-10）目的: `#` で始まる構文（ディレクティブ・属性）の視認性と、条件付きコンパイルブロックの構造の読みやすさを改善する。

## 背景（指摘4点）

1. VSCode拡張で `#end` がハイライトされない（`#endif` は定義済みだがCmは `#end`）
2. `#` で始まる構文全般にハイライトが必要
3. `#ifdef` は良いが `#[input]` 等の属性にもハイライトが必要
4. `#ifdef` があるとインデントが分かりづらい。モダンな言語としてブロック内容にインデントを追加してはどうか

## 設計判断

### インデント（指摘4）: 採用

Cmの `#ifdef` はC系の行指向ディレクティブと異なり、`#end` で明示的に閉じる**ブロック構文**である。C系の「ディレクティブはカラム0」という慣習に従う理由はなく、ブロック内容を1段インデントする方が構造が読める。

規則: **ディレクティブ（`#ifdef`/`#ifndef`/`#else`/`#end`）は外側のインデントレベル、ブロック内容は+1段**。ブレース・ブラケット・丸括弧の深さと合算し、ネストにも対応する。`cm fmt` が機械的に正規化し、冪等。

```cm
void f(posedge clk) {
    #ifdef TEST
        int x = 1;
    #end
}
```

プリプロセッサ・パーサは行頭空白に依存しないため意味論への影響はない。

### 条件ブロックのブロック扱い（改訂 2026-07-11）

初版の `ifdef_depth` フラットカウンタは、分岐ごとに波括弧が不均衡なケース（`#ifdef` 側と `#else` 側がそれぞれ `{` を開くパターン）で括弧カウントが分岐間に漏れ、以降のインデントが崩壊した。

改訂: 条件ブロックを波括弧と同様の**ブロック**としてスタック管理する。

- `#ifdef`/`#ifndef` で「その時点の括弧カウンタ + ディレクティブ出力深さ」をスタックにpush
- `#else`/`#end` は対応する `#ifdef` と**同じ深さ**に出力（常に同列に揃う）
- `#else` では括弧カウンタを分岐開始時点へ**復元**（前の分岐の波括弧不均衡を持ち越さない）
- `#end` では最後の分岐の括弧状態を持ち越してpop（両分岐が同型の `{` を開く定型パターンで後続の `}` と正しく対応）

あわせて、SV幅付きリテラル（`16'd256` 等）の `'` を文字リテラル開始と誤認して括弧カウントが狂う不具合を修正（lexerの `N'[dbhDBH]VALUE` 規則に合わせて全整形パスで除外）。

### 継続行インデントと行末コメント（改訂2 2026-07-11）

ユーザー指摘3点への対応。

1. **`#ifdef` のシンボル名ハイライト**: `#ifdef TEST` の `TEST` を`const` と同じ配色（`storage.type.primitive.cm`）でキャプチャする
2. **継続行のインデント**: 長い式の折り返しで、1回目の継続行を文の開始行より1段深くし、2回目以降も同じ深さに揃える。規則: **文の開始行と同じ括弧深さの継続行に+1段**。未閉括弧を持ち越す継続行（`(q0 |` の後の `|` 行等）は従来どおり括弧深さに従う（両者は結果的に同じ+1段の深さになる）。文の完結は「行末コメントを除いたコード末尾が `;` `{` `}` `,` のいずれか」で判定。コメント行・`#` 行・閉じ括弧で始まる行（末尾カンマなしの最終要素直後の `}` 等）は継続行として扱わない
3. **行末コメントの位置**: グループ単位の自動位置揃えを廃止し、手動調整を尊重する。コードとの間隔が2スペース未満の場合のみ2スペースへ広げる

あわせて `enforce_kr_braces` の潜在バグを修正: 裸ブロックの `{` や行末コメント付き行にも無条件で `{` を結合していたため、結合条件を「前の行が `)` `>` または識別子で終わり、行末コメントを含まない」に限定。

## 実装

- `fmt/formatter.cpp` `normalize_indentation`: `stmt_open` / `stmt_group_depth` による文の継続行トラッキング（改訂2）
- `fmt/formatter.cpp` `align_inline_comments`: 最小間隔（2スペース）の保証のみ行う方式へ簡素化（改訂2）
- `vscode-extension/syntaxes/cm.tmLanguage.json`: 条件ディレクティブのシンボル名キャプチャ（capture 3 = `storage.type.primitive.cm`）（改訂2）
- `fmt/formatter.cpp` `normalize_indentation`: `CondState` スタック（brace/bracket/paren スナップショット + ディレクティブ出力深さ）で条件ブロックをブロック扱い（上記改訂）
- `fmt/formatter.cpp` `is_sized_literal_quote`: 幅付きリテラル判定を全パス（インデント・演算子空白・セミコロン改行・コメント揃え）に適用
- `tests/integration/formatter_test.cpp`: ネスト・`#else` 同列揃え・分岐不均衡・幅付きリテラル・冪等性の回帰テスト
- VSCode `cm.tmLanguage.json`（`#` 構文の統一配色）:
  - 配色規則: **`#` = 青、属性の `[` `]` = 黄、中身・ディレクティブ名 = ピンク、`assign` = ピンク**
    - ディレクティブ `#ifdef` 等: `#` → `storage.type.directive`（青）、名前 → `keyword.control.directive`（ピンク）。`end` を追加（指摘1）
    - 属性 `#[...]`: 行内限定のbegin/end（endに行末フォールバック `(?=$)`）で`#`（青）・`[` `]`（黄）・中身（ピンク）・`::`（白＝punctuation）をトークナイズ（指摘3）。閉じない `#[` があっても複数行へピンクが漏れず、どのネスト・インデントでも同一ハイライト（vscode-textmate実エンジンによるトークナイズ検証済み）
    - コメント・文字列を属性より先に評価し、コメント内の `#[...]` の誤着色を防止
  - `#define`/`#undef`/`#error`/`#warning`/`#include` も同じ配色規則
  - 未知の `#ディレクティブ` のキャッチオール規則を追加（将来の構文）（指摘2）
- VSCode `language-configuration.json`:
  - indentationRules: `#ifdef`/`#ifndef`/`#else` で次行インデント増、`#end`/`#else` の行自体をデデント（エディタの自動インデント）
  - folding: `#ifdef`/`#ifndef` 〜 `#end` を折りたたみ可能に
  - `colorizedBracketPairs` を `{}` と `()` に限定。VSCodeのブラケットペア色付けはネスト深さで `[` `]` を塗り替える（struct内の属性括弧が深さ2のピンクになる）ため、角括弧を対象外にして tmLanguage の配色（`[` `]`=黄）を常に適用する
