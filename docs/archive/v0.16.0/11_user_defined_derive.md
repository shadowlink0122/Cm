# v0.16.0 実装設計 11: ユーザー定義derive可能interfaceの前方検討

優先度: 検討（ユーザー要望 2026-07-11。v0.16.0の実装対象外の前方設計）目的: `#[derive]`（設計10）の対象をコンパイラ組み込み8種から拡張し、ユーザー自身のinterfaceをderive可能にするために必要な言語機能（構造体メンバの読み取り・可変長引数）を設計する。

## 前提の確認: なぜ任意のinterfaceは自動実装できないか

- deriveの実体は「構造体の全フィールドに対する構造的帰納」である: Eqなら「全フィールドの`==`のAND」、Hashなら「全フィールドのhashの結合」のように、**フィールドごとの処理とその畳み込み方**が決まって初めて実装を機械生成できる。
- 現行実装ではこの規則がコンパイラ内部のC++にハードコードされている（`frontend/types/checking/auto_impl.cpp`のシグネチャ登録 + `mir/lowering/auto_impl*.cpp`の本体生成）。
- 任意のinterfaceのメソッド意味論をコンパイラが推測することは原理的に不可能なので、ユーザー定義deriveとは「フィールドごとの規則をCmコードで書けるようにすること」に他ならない。

## 必要な言語機能の分解

ユーザーがderive規則をCmで書くには、次の3つが必要になる。

1. **構造体メンバの読み取り**（コンパイル時イントロスペクション）: フィールドの個数・名前・型・値へのアクセス。
2. **異型フィールド列の反復**: フィールドごとに型が異なるため実行時ループでは型付けできず、コンパイル時に展開されるループが必要。
3. **derive可能interfaceの宣言**: 規則をinterfaceのデフォルト実装として書き、`#[derive]`がそれを各構造体へ実体化する仕組み。

可変長引数はこの分解では補助機能になる（後述: 大半のderiveはフィールド反復の畳み込みで書け、可変長が必須になるのはシグネチャ自体がフィールド数に依存するderiveのみ）。

## 機能1: 構造体メンバの読み取り（コンパイル時イントロスペクション）

### 提案構文

```cm
<T> string to_json(T value) {
    string out = "{";
    // fields(T) の for はコンパイル時にフィールド数ぶん静的展開される
    for (field f : fields(T)) {
        out = out + "\"" + f.name + "\": " + f.value(value).serialize() + ",";
    }
    return out + "}";
}
```

- `fields(T)` はコンパイル時にのみ存在するフィールド列を返す組み込み構文。
- `for (field f : fields(T))` はモノモーフィゼーション時に静的展開され、各反復は具象フィールド型で個別に型検査される。
- 反復変数から得られるもの: `f.name`（const string）、`f.index`（const int）、`f.value(式)`（該当フィールドへの型付きアクセス。lvalue）。
- 新キーワードは追加しない: `for` の反復対象が `fields(T)` のときだけ静的展開になる。`static for` のような専用キーワード案もあるが、`static` は既存キーワードであり、SVバックエンドの定数ループ静的展開と同じ機構に載せられる既存 `for` 構文の再利用を推奨する。

### 実現可能性

- Cmは全ジェネリクスをモノモーフィゼーション（MIR Pass 5）で単相化しており、「構造体ごとに本体を展開する」機構は自動実装生成（Pass 1.5 / Pass 5）として既に存在する。展開ベースのイントロスペクションはこの延長に載る。
- 実行時リフレクション（Goの`reflect`等）は採用しない: SV・UEFI・baremetalバックエンドでは実行時型情報を保持できず、コンパイル時展開なら全バックエンド中立になる。

### 制約・論点

- 対象はstruct型のみ（プリミティブ・enumへの適用はエラー。enumのバリアント反復は将来の別設計とする）。
- フィールド型への一括要求を表す境界構文が必要: `where fields(T): Eq`（全フィールド型がEqを実装していること）。これがないとC++テンプレート同様の「展開後エラー」になり診断が悪化する。
- privateフィールドの可視性: derive実体化の文脈（コンパイラ生成コード）では全フィールドを読めるべきだが、一般のジェネリック関数内の `fields(T)` がprivateを露出すると `private` の意味が壊れる。「derive文脈では全フィールド・一般文脈ではpublicのみ」の2段階可視性を提案するが、要追加検討（未解決課題参照）。

## 機能2: 可変長引数

可変長引数は**任意のユニオン型のスライス糖衣**として実現する（型パック＝可変長ジェネリクスは導入しない）。

### 設計: `T...` = `T[]` スライスへのパック

```cm
// 同種: int... は int[] スライスの糖衣
int sum(int... xs) {
    int total = 0;
    for (int x : xs) {
        total = total + x;
    }
    return total;
}

sum(1, 2, 3);  // 呼び出し側で配列にパックされる

// 異型: ユニオン型のスライスで任意の型の混在を受ける
typedef Loggable = int | string | bool;

void log_all(Loggable... items) {
    for (Loggable item : items) {
        // 要素の実型は静的に決まらないため、型判別はユーザーが実行時に行う
        match (item) {
            int i => println("int: {i}");
            string s => println("str: {s}");
            bool b => println("bool: {b}");
        }
    }
}

log_all(1, "two", true);
```

- 実体は「末尾パラメータ `T...` をスライス `T[]` として受け、呼び出し側で各実引数を `T` へ暗黙変換して配列にパックする」糖衣であり、既存のユニオン型 + スライス機構にそのまま載る。
- **スライス内の型順序は静的にチェックできない**: `Loggable...` に対して呼び出し側の並び（int, string, bool…）は型ごとには検査されず、各実引数が `Loggable` に代入可能かだけを検査する。要素ごとの実型の判別はユーザーが実行時（match等のユニオン型判別）で行う責務とする。
- この方式なら型パックなしで異型可変長を実現でき、実装コストは小さい（`println`系・min/max系のAPI改善として単独でも有用）。
- **前提機能（2026-07-11の検証で欠落を確認）**: 現状のCmには**ユニオン値の実行時型判別手段が存在しない**（上例のmatch型パターンは構文エラー、`is` 演算子も未実装、誤った型での `as` 取り出しはタグ検査なしでクラッシュする）。ユニオンはタグ付きで格納されているため、match型パターン（またはタグ検査付き `as` + `is`）の実装が本設計の前提となる。あわせてユニオン型スライスのpush/読み出しはv0.16.0で修正済み（バックエンド対応マトリクスの既知の問題を参照）。

### 可変長ジェネリクス（型パック）を導入しない理由

- C++のパラメータパック相当（`<T...>`）は型検査・モノモーフィゼーション・タプル型の全面対応が必要になり実装コストが特大。
- deriveの文脈で型パックが必須になるのは「シグネチャがフィールド数に依存する」規則のみ（例: 全フィールドを引数に取るコンストラクタの導出）だが、これもユニオンスライス糖衣 + 実行時判別で代替できる場合が多い。
- フィールドを畳み込むderive（Eq・Hash・Debug・Serialize等）は機能1のfor展開だけで書けるため、型パックは需要が具体化した時点で別設計として再検討する。

## 機能3: derive可能interfaceの宣言

機能1をinterfaceのデフォルト実装と組み合わせ、`#[derivable]` でderive可能であることを宣言する。

```cm
#[derivable]
interface Serialize {
    // default付きメソッドはderive時のテンプレート本体になる
    default string serialize() {
        string out = "{";
        for (field f : fields(Self)) {
            out = out + "\"" + f.name + "\": " + f.value(self).serialize() + ",";
        }
        return out + "}";
    }
}

#[derive(Serialize)]
struct Point {
    int x;
    int y;
}
```

- `#[derivable]` interfaceは全メソッドにdefault本体を持つことを要求する（シグネチャのみのメソッドが1つでもあればエラー）。
- `Self` は「deriveされる側の構造体型」を指す型キーワードとして新設する（値の `self`・`this` とは別物。予約語化が必要）。
- 暗黙の境界検査: default本体が `f.value(self).serialize()` のように各フィールドへ同メソッドを要求する場合、derive時に全フィールド型のSerialize実装を検査し、満たさない場合は「フィールド`x`の型`Y`が`Serialize`を実装していません」形式でフィールド名込みの診断を出す。
- 接続点: `#[derive(I)]` の名前解決を「組み込み8種 → ユーザー定義derivableレジストリ」の順で行う。組み込みとの名前衝突はエラー。
- 前提機能の追加が必要: 現行のinterfaceはシグネチャのみでdefault本体を受理しない（`parse_interface` は params の後に `;` 必須、`parser_decl.cpp:645-704`）。default本体のパース・HIR保持・derive時のインスタンス化（既存のモノモーフィゼーション機構を流用）が新規実装になる。
- 長期的には組み込み8種もこの機構の上のライブラリ（libs/）として再実装でき、コンパイラC++コード（auto_impl*.cpp群）を縮小できる（dogfooding）。

## 他言語比較

| 言語 | 方式 | Cmへの適合 |
|---|---|---|
| Rust | 手続きマクロ（TokenStream変換） | 不適合: マクロAPI・衛生性・安定したAST公開の維持負担が大きすぎる |
| Zig | comptime + `@typeInfo`/`@field` | 近い: 展開ベースでバックエンド中立。ただし汎用CTFEはCmには過剰 |
| D | コンパイル時リフレクション（`__traits`） | 近い: 静的展開の先行例 |
| C++26 | 静的リフレクション（P2996） | 方向性は同じだが仕様規模が大きい |
| Go | 実行時 `reflect` | 不適合: SV/UEFI/baremetalで実行時型情報を持てない |

Cmはモノモーフィゼーション前提のコンパイラであり、Zig/D系の「コンパイル時展開 + 限定イントロスペクション」が最も自然に適合する。

## 段階導入の推奨

| Phase | 内容 | 規模 | 時期の目安 |
|---|---|---|---|
| 0 | 組み込み8種 + `#[derive]`記法（設計10） | 小 | v0.16.0 |
| 1 | 可変長引数（ユニオン型スライス糖衣、機能2） | 小 | 独立機能として需要が出た時点 |
| 2 | `fields(T)` 静的展開 + `where fields(T): I` 境界（機能1） | 大 | v1.0.0以降を推奨 |
| 3 | `#[derivable]` + interfaceデフォルト実装 + `Self`（機能3） | 大 | Phase 2の後続 |
| 4 | 可変長ジェネリクス（型パック） | 特大 | 導入しない方針（ユニオンスライスで代替。需要が具体化した場合のみ再検討） |

- Phase 1以降はいずれも追加的（additive）な構文であり、既存コードを壊さずv1.0.0以降のマイナーバージョンでも導入できる。
- ただし**v0.18.0の仕様凍結時に予約だけ済ませておく**ことを推奨する: `Self`（型キーワード）、`fields`（組み込み構文名）、`derivable`（属性名）、`default` のinterface内用法。予約せずに凍結すると、後からの導入がユーザー識別子と衝突して破壊的変更になり得る（roadmap_v1.0.0の「予約語・構文の最終整理」項目に追加する）。
- 当面の実需（例: Default・Serialize等が欲しい）には組み込みderiveセットへの追加で対応する方が費用対効果が高い（既存機構に1種増やすコストは小さく、本設計のPhase 2〜3を待たずに済む）。

## 未解決課題（実装設計時に再検討）

- privateフィールドの可視性ルール（derive文脈と一般文脈の2段階可視性の是非）。
- enumへのderive（バリアント反復のイントロスペクション設計）。
- 再帰型・ポインタフィールドを含む構造体の扱い（現行組み込みderiveの挙動との整合）。
- `f.name` 等のconst string畳み込みとMIR最適化・SVバックエンドの文字列制約（24bit問題）との整合。
- derive展開コードのデバッグ体験（エラー位置の元ソースへの対応付け・展開結果のダンプ手段）。
